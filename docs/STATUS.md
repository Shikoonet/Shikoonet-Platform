**چهار پروسه، چهار اپ، دو در.** تا ۲۰۲۶-۰۸-۱۶ سه در بود و دو SPA: هابِ پرداخت روی `/` و پنل
فروشگاه روی `/admin/`، هرکدام پشت یک اپلیکیشن Cloudflare Access جدا با `aud` متفاوت. **همان دو
`aud` تنها چیزی بود که ادغام را غیرممکن می‌کرد** — یک باندل که از یک مسیر بار می‌شود فقط یک توکن
می‌تواند داشته باشد، پس نیمی از فراخوانی‌هایش حتماً ۴۰۱ می‌گرفت. برای همین اول ورود عوض شد و بعد
پنل‌ها یکی شدند. حالا یک باندل روی `/admin/` است، `/` یک ۳۰۲، و مرزِ `READ_ONLY` روی دادهٔ شخصی
که Access هیچ‌وقت نمی‌کشیدش تنها چیزی است که جدا نگه‌شان می‌دارد (`mayRead`، `access.ts:58`).

**درِ دوم داخل خودِ تلگرام است.** سه جدول تصمیم می‌گیرند چه کسی این فروشگاه را می‌گرداند و هر سه
حالا رابط دارند: `access_users` (هابِ پرداخت) · `access_users` روی سطح ادمین (پنل فروشگاه، با
مرزِ «عملیاتِ فروشگاه در برابر مشتریانش» — کاتالوگ و پنل و متنِ ربات خواندنی می‌مانند، هر چیزی که
اسمِ یک آدم را می‌برد نه) · و `admins` که اپراتورهای خودِ ربات‌اند، حالا با **یک مجوز به ازای هر
اکشن** از `admins.permissions` که از `0005_ops.sql` وجود داشت و هیچ‌کس دو طرفش چیزی ننوشته بود.
`{}` یعنی «هرچه این نقش همیشه معنا می‌داد» — خواندنش به‌عنوان deny-all پنل را یک‌جا از همه می‌گرفت.
OWNER همیشه می‌تواند، چون صفحه‌ای که این ردیف‌ها را ویرایش می‌کند از راه خودِ ربات باز می‌شود.

اندازه‌ها با `wc -l` روی `src/` گرفته شده‌اند (۲۰۲۶-۰۸-۱۶). ستون دوم شمار **فایل** تست است، نه مورد تست:

```

packages/db               ۵۵۱ خط    ۳ فایل    آداپتور Postgres ← این درزِ کل مهاجرت است
packages/seed           ۱٬۳۵۲ خط    ۱ فایل    دیتای قطعی برای تست + کاتالوگ فروشگاه
apps/ingest-worker      ۱٬۹۶۱ خط   ۱۲ فایل    تنها سطح عمومی: POST /api/v1/sms
packages/sms-parser     ۳٬۰۱۵ خط    ۸ فایل    پارس پیامک بانکی فارسی
packages/migrate        ۳٬۱۸۷ خط   ۱۰ فایل    MySQL + D1 → Postgres
packages/contracts      ۳٬۵۹۸ خط              قراردادها + متن و کیبورد پیش‌فرضِ ربات
packages/domain         ۶٬۹۸۸ خط   ۲۱ فایل    تطبیق، تایید، تحلیل، آداپتور پنل، رمز و TOTP
apps/bot               ۱۱٬۰۲۶ خط   ۳۶ فایل    long polling، خرید، تحویل، تمدید، کیف پول، تخفیف، معرفی، انبار، ادمین
apps/dashboard-worker  ۱۳٬۳۹۹ خط   ۴۰ فایل    API کل پنل + ورود اپراتور (به‌علاوهٔ ۴ فایل e2e)
apps/admin-web         ۲۵٬۸۰۸ خط   ۲۴ فایل    **کل پنل** — ۱۶ صفحهٔ فروشگاه + ۶ صفحهٔ مالی در `src/hub/`
```

`apps/dashboard-web` دیگر وجود ندارد. ۲۰۲۶-۰۸-۱۶ کل `src` و ۲۱ فایل تستش با `git mv` به
`apps/admin-web/src/hub/` و `test/hub/` رفت و پکیج حذف شد. سه چیز در همان قدم پیدا شد:

- **۳٬۵۱۰ خط مرده** (`MatchList.tsx`، `MoreMenu.tsx`، `ChangeAccountModal.tsx`،
  `LiveStatus.tsx`، `CommentPanel.tsx`) که از هیچ فایل `src` قابل دسترس نبودند — **قبل** از
  انتقال حذف شدند، چون پورت‌کردن کد مرده گران‌ترین اشتباه ممکن آن‌جاست.
- **`tsconfig.json` هاب `include: ["src"]` داشت** — یعنی ۲۲ فایل تستش **هرگز تایپ‌چک نشده
  بودند**. با یکی‌شدن پکیج‌ها هشت خطا بیرون افتاد که همه‌شان شکل‌هایی بود که از زیر تست عوض
  شده و کسی ندیده بود (`AccountListItem.status`، کلیدهای `Unread` در شمارنده‌ها، `IncomeItem`).
- **تستِ ثابتِ polling یک دایرکتوری تخت را می‌خواند.** بعد از انتقال همان اسکن به فایل‌های
  پنل نگاه می‌کرد و سبز می‌ماند بدون اینکه هیچ‌کدام از فایل‌هایی که برایشان نوشته شده بود را
  ببیند. حالا بازگشتی است و هر دو نیمه را می‌پوشاند.

## راه‌اندازی و اجرا

```bash
pnpm install
pnpm sim:up                                   # Postgres روی 5433، MySQL روی 3307

# اسکیما را بساز — دفتر `schema_migrations` می‌گوید کدام‌ها را قبلاً دیده
DATABASE_URL=postgres://shikoo:shikoo_local@127.0.0.1:5433/shikoo \
  corepack pnpm --filter @shikoo/db schema up

# ⚠️ `pnpm typecheck` و `pnpm lint` ریشه روی ویندوز اجرا نمی‌شوند — داخل خودشان
# `pnpm` خالی صدا می‌زنند که روی PATH نیست. مستقیم بزن:
corepack pnpm -r typecheck && corepack pnpm -r lint
corepack pnpm -r --workspace-concurrency=1 test   # ۱٬۹۸۳ تست، ۱۶۶ فایل، ۹ پکیج

# مرورگر واقعی — سرور و دیتابیس می‌خواهد، پس جزو `test` نیست
corepack pnpm --filter @shikoo/dashboard e2e      # ۲۳ سناریو

# دیتای شبیه‌سازی (پاک می‌کند و از نو می‌سازد — فقط روی دیتابیس محلی اجرا می‌شود)
pnpm --filter @shikoo/seed seed:sim
```

**تضمین‌های پول** (هر وقت شک کردی، روی هر دیتابیسی امن است — همه‌چیز rollback می‌شود):

```bash
docker exec -i shikoo-sim-postgres-1 psql -U shikoo -d shikoo \
  -v ON_ERROR_STOP=1 -q < migrations/verify_invariants.sql     # باید ۳۰ تا PASS بدهد
```

**مهاجرت دیتای واقعی:**

```bash
pnpm --filter @shikoo/migrate preflight   # فقط می‌خواند — هیچ‌چیز نمی‌نویسد
pnpm --filter @shikoo/migrate migrate     # preflight → مهاجرت → تایید پولی
pnpm --filter @shikoo/migrate verify      # دوباره دو طرف را مقایسه می‌کند
```

**اجرای سرویس‌ها:**

```bash
# ⚠️ `ENV_NAME` اجباری است و پیش‌فرض ندارد — یکی از local/test/staging/production.
# بدون آن پروسه بالا نمی‌آید. عمدی است: تا ۰۸-۱۸ پیش‌فرضش `local` بود و یک غلط
# تایپی همهٔ گاردهای پروداکشن را بی‌صدا خاموش می‌کرد.
ENV_NAME=local DATABASE_URL=postgres://shikoo:shikoo_local@127.0.0.1:5433/shikoo \
  pnpm --filter @shikoo/ingest start       # پورت 8787

ENV_NAME=local DATABASE_URL=... TEST_ACCESS_USER=you@example.com \
  pnpm --filter @shikoo/dashboard start    # پورت 8788

# ربات — بدون پورت، long polling. هرگز با توکن ربات واقعی.
# توکن را در sim/.env.local بنویس (git-ignored) و این را بزن؛ توکن به هیچ
# خط فرمانی و هیچ history شلی نمی‌رسد. فقط یک پروسه هم‌زمان می‌تواند poll کند.
pnpm --filter @shikoo/bot start:local
```

> `pnpm` روی ویندوز معمولاً روی PATH نیست. یا `corepack pnpm ...` بزن، یا یک شیم بساز:
> `%TEMP%\pnpmshim\pnpm.cmd` با محتوای `corepack pnpm %*` و آن پوشه را به PATH اضافه کن.
> اسکریپت `test` ریشه داخل خودش `pnpm` صدا می‌زند، پس بدون شیم کار نمی‌کند.

## عیب‌یابی — علامت ← علت ← درمان

### تست و دیتابیس

| علامت                                                   | علت                                                                                                                                                   | درمان                                                                                                                                                             |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| تست‌ها تصادفی قرمز می‌شوند، `TRUNCATE`/duplicate key    | دو پکیج هم‌زمان روی **یک** Postgres تست می‌گیرند و همدیگر را پاک می‌کنند                                                                              | `pnpm test` ریشه `--workspace-concurrency=1` دارد. نبودِ `--parallel` کافی **نیست** — فقط ترتیب توپولوژیک را نگه می‌دارد و پکیج‌های خواهر باز هم هم‌زمان می‌شوند. |
| `expected N tables, found 0` (الان ۵۷ جدول)             | اسکیما اعمال نشده                                                                                                                                     | حلقهٔ `migrations/0*.sql` بالا را اجرا کن. **`000*` ننویس** — از `0010` به بعد را نمی‌گیرد و بی‌صدا نصفه اعمال می‌شود.                                           |
| `duplicate key ... devices_pkey` در `verify_invariants` | فیکسچری با دیتای موجود تصادم کرده                                                                                                                     | نباید بشود — همهٔ فیکسچرها `__inv-` پیشوند دارند. اگر شد یعنی کسی پیشوند را برداشته.                                                                              |
| `audit_logs is append-only (attempted DELETE)`          | کد یا تستی می‌خواهد لاگ ممیزی را پاک کند                                                                                                              | این عمدی است. برای ریست در **تست** از `TRUNCATE ... CASCADE` استفاده کن، نه `DELETE`.                                                                             |
| تست وقتِ‌دار امروز سبز، فردا قرمز                       | `Date.now()` واقعی خوانده می‌شود ولی انتظار به تاریخ ثابت گره خورده                                                                                   | `vi.spyOn(Date,'now').mockReturnValue(NOW_MS)` در `beforeEach` و `vi.restoreAllMocks()` در `afterEach`                                                            |
| `ECONNREFUSED 127.0.0.1:5433` وسط اجرای تست             | Docker Desktop مُرده                                                                                                                                  | کانتینرها را دوباره بالا بیاور. **این قرمز را باگ کد نخوان** — قبلش کد خروجی را جدا از `tail`/`grep` نگاه کن، وگرنه کد خروجیِ لولهٔ آخر را می‌خوانی نه `pnpm` را. |
| `ports are not available: ... 5433 ... forbidden`       | ویندوز پورت را در بازهٔ رزرو Hyper-V بلعیده (`netsh interface ipv4 show excludedportrange protocol=tcp`)                                              | با ادمین: `net stop winnat ; net start winnat`. دائمی: `netsh int ipv4 add excludedportrange protocol=tcp startport=5433 numberofports=1 store=persistent`        |
| `duplicate key ... telegram_updates_pkey` در تست ربات   | دو تست از یک `update_id` استفاده کرده‌اند                                                                                                             | `ids()` در تست‌ها بلوک ۱۰تایی می‌دهد چون چند تست `updateId + 1` را هم مصرف می‌کنند. از همان استفاده کن، دستی عدد نگذار.                                           |
| ربات `409 Conflict` می‌گیرد                             | دو پروسه هم‌زمان روی یک توکن poll می‌کنند                                                                                                             | معمولاً پروسهٔ قبلی یتیم مانده. با `Get-CimInstance Win32_Process` دنبال `server.ts` بگرد و بکشش. کشتن شلِ والد بچه‌ها را نمی‌کشد.                                |
| ربات وسط تست دستی می‌گوید «برای شروع /start را بزنید»   | `pnpm test` اجرا شده و `resetBot()` روی `users` یک `TRUNCATE ... CASCADE` زده                                                                         | باگ نیست. وقتی روی ربات زنده تست دستی می‌گیری تست خودکار نگیر؛ اگر گرفتی، دوباره `/start` بزن.                                                                    |
| داشبورد محلی روی همه‌چیز `403` می‌دهد                   | `access_users` خالی است — تست‌ها truncate کرده‌اند. `TEST_ACCESS_USER` فقط JWT را رد می‌کند، نقش را نه                                                | یک ردیف `ADMIN` با همان ایمیل در `access_users` بگذار                                                                                                             |

### آداپتور Postgres (`packages/db`)

| علامت                                              | علت                                                  | درمان                                                                                                        |
| -------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `could not determine data type of parameter $2`    | کوئری از قطعات اختیاری ساخته شده و `$2` استفاده نشده | خودکار حل می‌شود (`compactParameters`). اگر باز دیدی، خطا **خودِ دستور را چاپ می‌کند** — از همان‌جا شروع کن. |
| `'4000000' !== 4000000` در مقایسهٔ پول             | `SUM(bigint)` در Postgres `numeric` است              | آداپتور numeric را عدد می‌کند. اگر عدد بیش از ۱۵ رقم معنادار باشد **خطا می‌دهد**، نه گرد کردن بی‌صدا.        |
| مقایسهٔ زمان یا مبلغ همیشه false                   | ستون `bigint` رشته برگشته                            | آداپتور `int8` را عدد می‌کند. بیرون از آداپتور کوئری نزن.                                                    |
| `column "fa.id" must appear in the GROUP BY`       | SQLite ستون غیرتجمیعی را قبول می‌کرد، Postgres نه    | کلید اصلی جدول را به `GROUP BY` اضافه کن؛ بقیهٔ ستون‌هایش را Postgres از روی وابستگی تابعی می‌پذیرد          |
| `EXISTS(...)` همیشه false                          | در SQLite عدد ۰/۱، در Postgres بولین                 | در SQL بنویس `(EXISTS (...))::int`                                                                           |
| کلید پاسخ `accountid` به‌جای `accountId`           | Postgres شناسه‌های بدون کوتیشن را کوچک می‌کند        | نام مستعار را کوتیشن بگذار: `AS "accountId"` — یا بهتر، snake_case بنویس                                     |
| `anonymous ? placeholder` یا `mixes ?N and bare ?` | یک دستور هر دو سبک را قاطی کرده                      | یکدست کن. مترجم عمداً حدس نمی‌زند.                                                                           |
| `INSERT OR IGNORE ... ON CONFLICT is ambiguous`    | هر دو با هم آمده‌اند                                 | یکی را بردار.                                                                                                |
| ۵۰۰ جایی که ۴۰۹ انتظار داری                        | `catch` دنبال `UNIQUE` در متن خطا می‌گردد — جملهٔ SQLite. Postgres `duplicate key value violates unique constraint` می‌گوید، با حروف کوچک | `isUniqueViolation(e)` از `@shikoo/db` که `SQLSTATE 23505` را می‌سنجد. هرگز روی متن خطا شرط نگذار.            |

### مهاجرت دیتا

## تله‌هایی که یک بار گازمان گرفتند

**۱. `Move-Item` روی پوشهٔ بزرگ نیمه‌کاره تمام می‌شود و خطا هم می‌دهد.** یک بار `.git` کامل این‌طور
رفت و بعد با `Remove-Item -Recurse` پاک شد. از `robocopy <src> <dst> /E` استفاده کن، قبل از حذف
مقصد را بشمار، و cwd هیچ شلی داخل پوشهٔ در حال جابه‌جایی نباشد.

**۲. `GROUP BY` در MySQL به بزرگی حروف حساس نیست.** بررسی اول من مقدار `active` (کوچک) را ندید
چون با `Active` یکی شمرده شده بود. هر بررسی مقدارِ یکتا روی MySQL باید `COLLATE utf8mb4_bin` داشته
باشد — **چک باید دست‌کم به سخت‌گیریِ کدی باشد که چک می‌کند.**

**۳. تستی که فقط با خودش سازگار است هیچ چیز را ثابت نمی‌کند.** باگ ۷ ساعتهٔ «امروز به وقت تهران»
سال‌ها زنده ماند چون تست‌ها فقط بررسی می‌کردند تابع با خودش می‌خواند. حالا با `Asia/Tehran` واقعی
سنجیده می‌شود.

**۴. جداسازی تست‌ها که از پلتفرم می‌آمد، با انتقال ناپدید می‌شود.** Workers به هر فایل تست یک
دیتابیس تازه می‌داد. با یک Postgres مشترک، چهار باگ فیکسچر بیرون زد که سال‌ها پنهان بودند.

**۵. دیتای seed از قبل تضمین پول را نقض می‌کرد** — و کسی نفهمید چون تست‌های seed مهاجرت `0011`
(همان که ایندکس‌های partial unique را می‌سازد) را اعمال نمی‌کردند.

## تصمیم‌هایی که نباید بی‌دلیل عوض شوند

- **تضمین پول در ایندکس است، نه در کد.** `idx_match_one_auto_per_tx` و
  `idx_match_one_auto_per_claim`. یک تراکنش بانکی حداکثر یک claim را تسویه می‌کند. **دلیل اصلی
  انتخاب Postgres همین است** — MySQL ایندکس شرطی ندارد.
- **پول همه‌جا `bigint` ریال.** تومان فقط در لبهٔ ربات وجود دارد.
- **کیف پول دفتر کل است.** هیچ کدی `wallets.balance_irr` را نمی‌نویسد؛ ردیف در `wallet_entries`
  درج می‌شود و تریگر مانده را جابه‌جا می‌کند.
- **`0004_payment_hub.sql` یک پورت مکانیکی است، نه بازطراحی.** اپاک میلی‌ثانیه `bigint` ماند و
  پرچم‌های ۰/۱ `smallint` — چون ۸۰۰ تست و کل `packages/domain` این ستون‌ها را می‌خوانند.
- **مهاجرت هیچ‌وقت پول را دست‌کاری نمی‌کند.** مانده منفی `-5,940,000` تومان عیناً منتقل می‌شود.
  تصحیح‌های آگاهانه فقط در `corrections.ts` با شواهدشان.
- **`legacy/` فقط مرجع است.** کد زنده نیست. در فاز ۵ حذف می‌شود.
- **آپدیت تلگرام در همان تراکنشی claim می‌شود که اثرش را می‌نویسد.** `handleUpdate` همه‌چیز را داخل
  یک `withSession` می‌گذارد و اولین کارش درج در `telegram_updates` است. اگر بعدش چیزی بترکد، claim
  هم rollback می‌شود و تحویل بعدی تلگرام یک تلاش واقعی است. جدا کردن این دو یعنی یا کیف پول دوبار
  شارژ می‌شود یا آپدیت بی‌صدا گم می‌شود.
- **پاسخ‌ها بعد از commit فرستاده می‌شوند، نه داخل تراکنش.** پیامی که رفته با ROLLBACK برنمی‌گردد.
  هزینه‌اش این است که یک پاسخ ممکن است گم شود؛ در ازایش دیتابیس هیچ‌وقت غلط نمی‌شود.
- **آفست long polling ذخیره نمی‌شود.** تضمین یکتایی فقط `telegram_updates` است — دو سازوکار که
  بتوانند با هم اختلاف پیدا کنند بدتر از یکی است.
- **`callback_data` ورودی کاربر است، نه توکنی که ما داده‌ایم.** تلگرام امضایش نمی‌کند و یادش نیست
  چه دکمه‌ای به چه کسی نشان داده؛ هر کسی با یک فراخوان ساده هر رشته‌ای می‌فرستد. پس شناسه‌ای که از
  آن می‌آید **هرگز به‌تنهایی ردیف انتخاب نمی‌کند**. هر خواندنِ ردیفِ متعلق به مشتری از `owned.ts` رد
  می‌شود که همهٔ کوئری‌هایش `AND user_id = $caller` دارند و تماس‌گیرنده آرگومان اولشان است، نه یک
  گزینه. ربات PHP همین را دستی در هر هندلر می‌گذاشت و در `subscriptionurl_` جا انداخت — مورد ۸
  `BUGS-FOR-ADMIN.md`. تستی هست که همان حمله را انجام می‌دهد.
- **آفستی که `pollOnce` برمی‌گرداند «رسید» است، نه بیشترین شماره.** تلگرام با گرفتن آن، هر آپدیت
  پایین‌ترش را **پاک می‌کند**. پس آفست فقط تا درست قبل از اولین آپدیتی که هندلرش ترکید جلو می‌رود.
  اگر از رویش رد شویم، rollbackِ claim هیچ چیزی نخریده — تلگرام دیگر آن را نمی‌فرستد. و وقتی
  دیتابیس خواب است این یعنی از دست رفتن **کل بسته**، نه یک پیام. آپدیت‌های بعد از خطا همچنان
  پردازش می‌شوند تا صف نخوابد؛ دور بعد دوباره می‌آیند و claim آن‌ها را `duplicate` می‌کند.
- **بسته‌ای که هیچ پیشرفتی نداشت، قبل از تلاش بعدی مکث می‌کند.** وقتی آپدیت در صف باشد
  `getUpdates` بلافاصله برمی‌گردد و long-poll نمی‌کند؛ اگر هندلرها هم بترکند هیچ چیز حلقه را کند
  نمی‌کند. اندازه‌گیری واقعی روی قطعیِ ۵ دقیقه‌ای Postgres: **۳۵۰ تلاش و ۶٬۳۶۳ خط لاگ**. با مکث،
  همان سناریو به ~۰.۱ چرخه در ثانیه رسید. بدون این، روی سرور واقعی از تلگرام `429` می‌گیریم و
  دیتابیسی را که دارد بلند می‌شود می‌کوبیم.
- **نشان‌داده‌شدن دکمه هیچ چیزی را اثبات نمی‌کند.** شرط دیده‌شدن یک محصول فقط یک بار نوشته شده
  (`PURCHASABLE` در `catalog.ts`) و مسیر ثبت سفارش **همان** را دوباره اجرا می‌کند. لیست با یک
  قاعده و فروش با قاعده‌ای دیگر، دقیقاً همان‌طور از هم فاصله می‌گیرند که در ربات PHP `config_`
  چک دارد و `subscriptionurl_` ندارد.
- **قیمت داخل همان تراکنشی از دیتابیس خوانده می‌شود که سفارش را می‌نویسد.** مشتری انتخاب می‌کند
  _کدام_ پلن؛ _چند_ دست او نیست. و تخفیف ایستادهٔ مشتری (`users.discount_percent`) واقعاً اعمال
  می‌شود — هشت مشتری پروداکشن ۱۰ تا ۱۰۰ درصد دارند و نادیده‌گرفتنش یعنی اضافه‌گرفتن از همه‌شان.
  قیمت فهرست روی ردیف سفارش می‌ماند تا فروش تخفیف‌خورده قابل حسابرسی بماند.
- **تابعی که «چند وقت پیش» را می‌سازد، مُهر زمانی می‌گیرد نه مدت.** قبلاً `formatRelativePast(ms)`
  بود و کنار `formatDuration` و `formatDurationLong` می‌نشست که واقعاً مدت می‌گیرند؛ دو تا از سه
  فراخوانش `verifiedAt` را مستقیم می‌دادند و کل epoch به‌عنوان فاصله فرمت می‌شد. روی داشبورد
  زنده این یعنی «Verified 29773038 minutes ago» (۵۶ سال) برای پرداختی که همان بعدازظهر تایید
  شده بود، در حالی که تب بغلی‌اش — تنها فراخوانی که تفریق را یادش بود — درست بود. حالا پارامتر
  خودِ مُهر زمانی است، چون همان چیزی است که هر فراخوان در دست دارد. `now` تزریق‌شدنی است تا تابع
  خالص بماند.
- **`answerCallbackQuery` بیرون از `handleUpdate` است.** آپدیت تکراری اصلاً به هندلر نمی‌رسد،
  ولی اسپینر دکمه‌اش باید بایستد؛ در قطعی دیتابیس هم باید بایستد، وگرنه ربات «هنگ‌کرده» دیده
  می‌شود.

از دفتر قدیمی‌تر است، `up` امتناع می‌کند تا یک بار baseline بخورد:

```

schema up                                 # 0022 و 0023
schema status                             # باید بگوید current
```

**۳. ربات باید ادمین کانال باشد.** این تنها قلمی است که هیچ کدی نمی‌تواند انجام دهد و

#### در برنامه — دو کاری که مسیر پنل را از حدس درمی‌آورند (تصمیم Sam، ۲۰۲۶-۰۸-۱۳)

هر دو از یک درس آمدند: نوشته بودم شکل `expire` را «فقط پنل واقعی مشخص می‌کند»، و بعد معلوم

**۱. خوانندهٔ `openapi.json` پنل — ✅ ساخته شد (۲۰۲۶-۰۸-۱۳)**

```bash
corepack pnpm --filter @shikoo/domain panel:schema https://panel.example.com
```

**فقط-خواندنی، و ساختاری این‌طور است:** تنها درخواستی که از پروسه بیرون می‌رود یک `GET` روی
`<panel>/openapi.json` است. نه لاگین، نه توکن، نه هیچ حسابی خوانده یا عوض می‌شود.

نکتهٔ طراحی‌اش این است که فهرست «فیلدهایی که می‌فرستیم» **دستی نوشته نشده**. اسکریپت
`provision` و `renew` واقعی را روی یک `fetch` ضبط‌کنندهٔ درون-پروسه‌ای اجرا می‌کند و همان
بدنه‌هایی را که آداپتور ساخته با اسکیمای پنل می‌سنجد. پس چیزی که چک می‌شود **همان چیزی است
که فرستاده می‌شود** — یک کپی دوم از `marzban.ts` نیست که فردا از آن جدا بیفتد.

خروجی برای هر فیلد یکی از چهارتاست: `ok` · `type-mismatch` · `not-in-schema` ·
`undeclared-type`. کد خروجی ۰ وقتی همه‌چیز جور است و ۱ وقتی آدمی باید نگاه کند.

**`not-in-schema` سرِ همان سوال باز است:** اگر `note` روی `UserModify` اعلام نشده باشد،
`PUT` باز هم موفق می‌شود و مقدار فقط دور ریخته می‌شود — یعنی نگهبانِ دومِ یک‌بار-اجرای تمدید
چیزی را می‌خواند که هرگز ذخیره نشده. صدای این خرابی صفر است، و این ابزار برای همین ساخته شد.

منطق سنجش خالص است و در `packages/domain/src/provisioning/schemaCheck.ts` با ۱۴ تست آفلاین
می‌نشیند؛ اسکریپت فقط `fetch` را اضافه می‌کند.

### پیامی که مشتری طلبکار است — ۲۰۲۶-۰۸-۱۸

`H-07`. همان شکل `C-01`، این‌بار سمت تلگرام. کامنت خودِ کد اعترافش را نوشته بود:

> «ردیف از قبل جلو رفته، پس این پیام دوباره تولید نمی‌شود. از دست‌دادنش هزینهٔ
> دو بار نفرستادن است.»

**این معامله برای یک فروشگاه برعکس است.** تلگرام چند ثانیه جواب ندادن عادی است؛ مشتری‌ای
که پول داده و هرگز خبردار نشده عادی نیست. و آن «دو بار نفرستادن» که بابتش پیام قربانی
می‌شد، با یک کلید که از خودِ رویداد ساخته می‌شود بسیار ارزان‌تر تضمین می‌شود.

**مهاجرت `0024`** جدول `bot_notifications` را می‌سازد: `dedupe_key` یکتا، `attempt_count`،
`next_attempt_at`، و `PENDING/SENT/FAILED/DEAD`. عمداً هم‌شکل `webhook_deliveries` — دو
outbox که رفتار متفاوت دارند یک چیز اضافه برای یادآوری در ساعت سه صبح است.

**چهار sweep تغییر کردند.** به‌جای برگرداندن `Notification[]`، داخل همان تراکنشی که ردیف
را جلو می‌برد `enqueue` می‌کنند. `flush` در `poll.ts` بعد از همهٔ sweepها می‌فرستد و اجازه
دارد شکست بخورد — تا آن لحظه پیام دیگر ماندگار است.

| sweep | کلید یکتایی | تراکنش |
| --- | --- | --- |
| `settle` تایید پرداخت / شارژ کیف | `settle:<payment public id>` | ✅ داخل |
| `expire` انقضای فاکتور | `expire:<order public id>` | ✅ داخل |
| `warn` هشدار اتمام سرویس | `warn:<sub id>:<reason>` | ✅ داخل (تراکنش تازه دورش کشیده شد) |
| `provision` تحویل سرویس | `provision:<order public id>` | ⚠️ بلافاصله **بعد** از commit |

**آن یک مورد صادقانه علامت خورده است** (`ponytail:` در `provision.ts`). `deliver` و `renew`
از **هشت خروجی در چهار تراکنش** به پیام می‌رسند و یکی‌شان مسیر ریفاند است؛ رد کردن enqueue
از همهٔ آن‌ها یعنی دست‌بردن در مسیر پول برای بستن پنجره‌ای به اندازهٔ یک insert محلی. آنچه
**بسته شد** همان خرابی‌ای است که واقعاً اتفاق می‌افتد: ردشدن پیام توسط تلگرام.

**`TelegramRejection` تازه است.** قبلاً `error_code` دور ریخته می‌شد و فقط متن می‌ماند.
outbox باید «تلگرام حالش بد است» را از «این مشتری ربات را بلاک کرده» تشخیص دهد — اولی هشت
تلاش می‌ارزد و دومی هیچ. تشخیص از روی **متن** امروز کار می‌کرد و روزی که تلگرام جمله‌اش را
عوض کند می‌شکست.

**اثبات با برداشتن:** حذف `isPermanentRejection` → دقیقاً تست «۴۰۳ را فوراً رها کن» قرمز.
حذف lease از `UPDATE` مدعی → دقیقاً تست هم‌زمانی قرمز. و دو ادعای تازه در
`verify_invariants.sql` (مجموع **۳۲**) که یکتایی `dedupe_key` را در خود Postgres می‌سنجند،
از جمله این‌که پیامِ **ارسال‌شده هم کلیدش را آزاد نمی‌کند**.

**و یک تستی که جا مانده بود، پیدا شد چون همان اثبات دوباره اجرا شد.** enqueueِ `settle` را
از داخل تراکنش بیرون بردم — یعنی دقیقاً همان باگ — و **هر ۱۸ تست سبز ماندند.** هیچ‌کدام
خاصیت تراکنشی را نمی‌سنجید؛ همه‌شان فقط می‌دیدند که پیام آخرش در جدول هست. این همان تلهٔ
`C-01` بود، دو برش بعد، در فایل دیگر.

تست درست همان الگو است: یک `CHECK` موقت روی `bot_notifications` که فقط کلید همین پرداخت را
رد می‌کند، و ادعا این‌که آن‌وقت **پرداخت اصلاً settle نشود** (`AWAITING_PAYMENT` /
`AWAITING_REVIEW` بماند) و بعد از برداشتن مانع، sweep بعدی عادی تمامش کند. با کد درست سبز
است؛ با enqueue بیرون از تراکنش **فقط همان یکی** قرمز می‌شود، با پیام
`{ order: 'PAID', payment: 'PAID' }` — که خودِ خرابی است: پول گرفته شده و کسی طلبکار چیزی
نیست.

**درسش تکرار قاعدهٔ ۶ روی خودِ اثبات است:** «اثبات با برداشتن» را باید *واقعاً اجرا کرد*،
نه این‌که در پیام کامیت نوشت که انجام شده.

### رسید از گیت رد می‌شود — ۲۰۲۶-۰۸-۱۸

`H-09` / `P0-03` بازبینی Codex. بازتأیید مستقل روی HEAD: گیت در
[`handle.ts:303`](../apps/bot/src/handle.ts#L303) **قبل از** تشخیص عکس و فایل اجرا می‌شود، و
رسید در ۳۲۵ و ۳۳۴ پردازش می‌شود. یعنی مشتری‌ای که پول را به کارت فرستاده و بین خرید تا
آپلود از کانال خارج شده، **تنها مدرک پرداختش را نمی‌تواند بدهد** — و صفحه‌ای که می‌بیند
می‌گوید «عضو کانال شو»، که کارِ درستی نیست چون عضو شدن رسیدِ در دستش را تحویل نمی‌دهد.

**رسید خرید نیست؛ نیمهٔ دوم خریدی است که قبلاً اتفاق افتاده.** پس از گیت رد می‌شود.

**و چیزی به کسی نمی‌دهد.** `handleReceipt` دنبال پرداختی می‌گردد که واقعاً منتظر است و
اگر نبود `RECEIPT_NOTHING_WAITING` می‌گوید — پس یک غیرعضو بدون سفارش هیچ‌چیز یاد نمی‌گیرد و
هیچ‌چیز نمی‌گیرد. گیت جلوی **هر راهی که خرید را شروع کند** سر جایش است. برای همین شرط
`carriesReceipt` است نه «هر پیامی»: بدون آن، گیت به اندازهٔ یک عکس پهنا داشت.

**دو تست، و اثبات با برداشتن:** «مشتری‌ای که از کانال خارج شده باز هم رسید می‌فرستد» —
و ادعای اضافه‌اش این است که `api.calls` **خالی** بماند، یعنی گیت اصلاً مشورت نشد، پس یک
تلگرامِ خراب یا ردیف کانالِ غلط هم این مسیر را نمی‌شکند. دومی: غیرعضو با عکس
`RECEIPT_NOTHING_WAITING` می‌گیرد و بلافاصله بعدش `/start` همان کاربر **صفحهٔ گیت** را
می‌گیرد. برداشتن `!carriesReceipt` → دقیقاً همین دو قرمز، و **۱۹ تست گیت دیگر سبز**، که
همان چیزی است که باید ثابت شود: گیت ضعیف نشده.

**یک تلهٔ تست که خودش را نشان داد:** `ids()` در این فایل یک‌یکی جلو می‌رود و تست اول سه
شناسه مصرف می‌کند؛ برخوردشان یعنی آپدیت **تکراری**، که بی‌صدا بدون پاسخ برمی‌گردد و شبیه
ادعای غلط به نظر می‌آید. و teardown فایل هم باید CASCADE می‌شد — تا امروز این فایل فقط
کاربر خالی می‌ساخت و اولین مشتریِ دارای سفارش، teardown را با خطای کلید خارجی شکست، **بعد
از این‌که همهٔ ۵۷۹ تست سبز شده بودند.**

### ده بایت گفت و شصت‌وچهار کیلوبایت فرستاد — ۲۰۲۶-۰۸-۱۸

**تست اول قرمز بود، و شکلِ قرمزی‌اش خودِ باگ است:** پاسخ **۴۰۰** آمد نه ۴۱۳ — یعنی ۶۴

سقف بدنه قرار بود نگذارد انجام شود. جفت هدر دستی نوشته می‌شود چون **همان حمله است**: هیچ

`CVE-2026-44456` (`<4.12.16`، chunked بدون طول) به ما **تصادفاً** نمی‌خورد: آن‌جا سقف بعد
از اجرای هندلر اعمال می‌شود، پس هندلری که بدنه را کامل نمی‌خواند ۲۰۰ می‌گیرد. هر دو هندلر ما
`await c.req.text()` می‌کنند، پس شمارنده سر وقت می‌ترکد. «تصادفاً امن» ثبت می‌شود چون

**ارتقا: `4.6.7` → `4.13.3`** (آخرین نسخه) روی هر دو worker، پین دقیق مثل قبل.
بعدش `pnpm audit`: **صفر یافته روی Hono**، از ۳۸ تا.

### کش‌بکی که صفر شد چون کسی نپرسید صفر یعنی چه — ۲۰۲۶-۰۸-۱۸

`H-08` / `P0-05`. بازتأیید مستقل روی HEAD: `loadShopSettings`
([`settings.ts`](../apps/bot/src/settings.ts)) هر خطای خواندن را می‌گیرد و **کل**
`DEFAULT_SHOP_SETTINGS` را برمی‌گرداند — که در آن `renewCashbackPercent` صفر است. و
`provision.ts` این را **بعد از** تماس موفق با پنل می‌خواند.

**یعنی:** یک خطای گذرای دیتابیس روی همان یک کوئری، در فاصلهٔ بین «پنل حساب را تمدید کرد» و
«سفارش COMPLETED شد»، تمدید را با کش‌بک صفر نهایی می‌کند. مشتری روزهایش را گرفته، پولش را
داده، و ۵٪ی که طلبش بود بی‌صدا نرفته — و **هیچ سوییپی به یک سفارش COMPLETED دوباره نگاه
نمی‌کند.** کامنتِ بالای همان خط دقیقاً همین را توجیه می‌کرد: «خواندن نباید تمدیدی را که پنل
اعمال کرده rollback کند.» درست بود و به همین دلیل جای خواندن غلط بود.

**تشخیصِ اصلی این برش یک بیت است:** پیش‌فرض‌ها برای سوییچ‌ها **درست‌اند** — فروشگاهی که
تنظیماتش خوانده نشد باید همان چیزی را بفروشد که دیروز می‌فروخت. برای درصدها نیستند. و از
بیرون این دو حالت یک شکل‌اند: «ادمین کش‌بک نمی‌دهد» و «نتوانستیم بپرسیم» هر دو صفر می‌دهند.
پس `ShopSettings.fromDatabase` اضافه شد — تنها چیزی که آن دو را از هم جدا می‌کند. جدول
**خالی** هم `true` است: «ادمین چیزی تنظیم نکرده» یک واقعیت است، «نتوانستیم بپرسیم» نیست.

**و درمان جای خواندن است، نه گاردِ تنها.** نرخ حالا قبل از `adapter.renew` خوانده می‌شود.
اگر حدسی بود، سفارش به `PAID` برمی‌گردد و `null` برمی‌گردد — همان مسیر retryable که از قبل
بود. هیچ کار برگشت‌ناپذیری انجام نشده، پس هزینه‌اش **یک سوییپ** است، نه ۵٪ مشتری. افزودنی
(`ADD_VOLUME`/`ADD_TIME`) کش‌بک نمی‌دهد و اصلاً منتظر این نمی‌ماند.

**تست، و اثبات با برداشتن:** جدول `settings` واقعاً `RENAME` می‌شود، نه mock — چیزی که زیر
آزمون است خودِ `catch` لودر است، و یک stub که پیش‌فرض‌ها را برمی‌گرداند فقط ثابت می‌کند این
تست بلد است آن‌ها را بسازد. ادعاها: پنل **اصلاً صدا نشد** (`panel.puts` خالی)، سفارش `PAID`
ماند، هیچ ردیف کش‌بکی نیست — و بعد از برگرداندن نام جدول، همان سوییپ تمدید **و** ۵٪ را
می‌دهد. برداشتن گارد → **دقیقاً همان یکی قرمز، ۲۲ تست دیگر renew سبز.**

**چه چیزی ساخته نشد:** «snapshot نرخ روی سفارش» که در صف نوشته بودم. شکافی که می‌بندد این
است که ادمین بین سفارش و تحویل نرخ را عوض کند — فاصله‌ای چنددقیقه‌ای که هر دو سرش یک نرخِ
واقعیِ تنظیم‌شده است. ضرر آن‌جا نبود؛ ضرر **حدس** بود.

**یک چیز که عوض نشد و عمدی است:** `settle.ts` هم `commissionPercent` را از همان لودر
می‌خواند و پیش‌فرضش ۱۰ است — دقیقاً همان عددی که پروداکشن دارد. آن‌جا کل تسویه در یک
تراکنش است و خطا rollback می‌شود؛ و ضررِ ممکنش «فروشگاه بیش‌تر می‌دهد» است، نه «مشتری کم‌تر
می‌گیرد». بستنِ آن مسیر یعنی پرداخت‌ها اصلاً تسویه نشوند تا دیتابیس خوب شود، که بدتر است.
حالا `fromDatabase` هست اگر روزی نظر عوض شد.

### تحویل واقعی روی پنل تست، و گاردی که بالاخره با خرابیِ ساختگی سنجیده شد — ۲۰۲۶-۰۸-۱۹

پنل تستِ اختصاصی (`pasa.fallumi.ir`، PasarGuard 5.2.1) از ۰۸-۱۸ هست و اعتبارنامه‌اش در
`sim/.env.local` است. تا امروز فقط با یک اسکریپت یک‌بارمصرف صدا زده شده بود؛ کاتالوگ سیم به آن
وصل نبود، و ردیف‌هایی که دستی ساخته شده بودند هنوز `base_url` پنل **قلابی** را داشتند.

**`panel:wire-test`** ([`wire-test-panel.ts`](../apps/bot/scripts/wire-test-panel.ts)) آن سه
ردیف — provider، محصول، پلن — را از روی env می‌سازد و idempotent است. در seed نیست چون آدرس و
رمز پنل نباید وارد گیت شوند؛ دستی هم نیست چون ردیف دستی با اولین بازسازی سیم می‌رود و همان
است که باعث شد `base_url` نیمه‌کاره بماند. گاردش قبل از نوشتن هاست را می‌سنجد: روی هر
دیتابیس غیرمحلی با کد ۲ رد می‌شود — تست شد، چون این جدول تصمیم می‌گیرد سفارش مشتری کجا تحویل
شود.

**`panel:preflight` بالاخره با یک خرابیِ عمدی سنجیده شد.** تا امروز تنها شاهدش گروه ۴۲ بود که
از قبل نبود — یعنی گارد هرگز روی خرابی‌ای که خودمان ساختیم آزمایش نشده بود. حالا هر دو جهت:

| گروهِ پیکربندی‌شده | خروجی |
| --- | --- |
| `[1]` (واقعاً روی پنل هست) | `✓ سرویس تست · ۱۰ گیگ / ۳۰ روز — [1]` |
| `[999]` (عمداً وجود ندارد) | `✗ … sends [999], panel does not have [999]`، خروج ۱ |

**و یک تحویل کامل از مسیر کد واقعی.** سفارش `PAID` در سیم → `provisionPaidOrders` (نه
اسکریپت دست‌ساز، نه بدنهٔ دستی) → پنل واقعی. سفارش `COMPLETED` شد، ردیف `subscriptions`
نوشته شد، و **خود پنل** تایید کرد:

```
HTTP 200  username=779001_pnlmsztax4w  status=active
data_limit=10737418240   ← دقیقاً ۱۰ گیگ، بایت به بایت
expire=2026-09-18T08:10:50.052000Z  ← تا میلی‌ثانیه برابر expires_at ما
group_ids=[1]            subscription_url طول ۶۹
```

حساب در `finally` حذف شد (`DELETE → 204`). این حقیقت بیرونی است به معنای قاعدهٔ ۶: ادعای ما
با پاسخ خود پنل سنجیده شد، نه با تابعی که خودمان نوشته‌ایم.

**چه چیزی هنوز باز است:** `panel:schema` روی این پنل هم جواب نمی‌دهد (`/openapi.json` اینجا
هم ۴۰۴ است)، پس شکل دقیق `UserCreate`/`UserModify` همچنان از سورس PasarGuard استنتاج
می‌شود نه از خود پنل.

### چیزی که رها می‌شود باید جایی بماند — ۲۰۲۶-۰۸-۱۸

`P0-04`. `MAX_UPDATE_ATTEMPTS = 3` سر جایش می‌ماند و دلیلش هم عوض نشده: یک آپدیت سمی
نباید صف را برای همه قفل کند. ولی رها کردن **قطعی** است — ack یعنی تلگرام آپدیت را پاک
می‌کند و دیگر هرگز نمی‌فرستد. تا امروز تنها ردّش یک `console.error` بود. اگر آن آپدیت
«پرداخت کردم» یا یک رسید بود، کارِ مشتری رفته بود و هیچ‌جا چیزی نبود که با آن پیدایش کنی.

**درمان:** جدول `telegram_dead_updates` (مهاجرت `0025`) — کل payload به‌صورت `jsonb`،
تعداد تلاش‌ها، و آخرین خطا. نوشتن **قبل از** ack انجام می‌شود، چون بعدش دیگر چیزی برای
نوشتن نیست. `ON CONFLICT` جمع می‌زند نه اضافه‌ردیف: تلگرام می‌تواند آپدیتِ ack‌نشده را
دوباره بفرستد و شمارندهٔ درون‌حافظه با هر restart صفر می‌شود، پس یک شناسه می‌تواند دو بار
به این‌جا برسد و دو ردیف مثل دو مشتری خوانده می‌شود.

**خطای مرگ هم ذخیره می‌شود، و این نکتهٔ ظریفِ برش بود:** شکست سوم در یک چرخه اتفاق می‌افتد
و رها کردن در چرخهٔ **بعدی**؛ تا آن موقع علتِ مرگ فقط در یک لاگ است. پس `attempts` حالا
`Map<number, Attempt>` است و دلیل را با شمارنده حمل می‌کند.

**اگر خودِ ثبت شکست بخورد، باز هم رها می‌کند — و این انتخاب است نه غفلت.** رها نکردن یعنی
صف دوباره پشت آپدیت سمی می‌ایستد؛ همان قفلی که این شمارنده برای جلوگیری از آن هست، و به
دلیلی به سادگیِ «مهاجرت هنوز روی آن باکس اجرا نشده». لاگ در آن حالت صریح می‌گوید
`AND NOT KEPT`.

**اثبات با برداشتن — و بار اول دروغ گفت.** تست «ردیف هست» با حذف نوشتن **سبز ماند**:
`ids()` از یک پایهٔ ثابت می‌شمارد، پس هر اجرا همان `update_id` را می‌دهد و ردیفِ
اجرای قبلی جواب می‌داد. ریشه در `BOT_TABLES` بود که جدول تازه در آن نبود؛ درمان همان‌جا
رفت، نه در تست. حالا تست اول `toBeNull()` را ادعا می‌کند و بعد نوشتن را. با برداشتن
نوشتن: **دقیقاً همان یکی قرمز، ۲۲ تست دیگر poll سبز.** تست دوم جدول را واقعاً
`RENAME` می‌کند و ثابت می‌کند صف با وجود ثبتِ شکسته جلو می‌رود.

**پاکسازی:** `pruneUpdates` حالا نامه‌های مرده را هم بعد از ۳۰ روز پاک می‌کند — پنجرهٔ
جدا از ۷ روزِ claim، چون سوال دیگری است: چقدر طول می‌کشد تا آدمی متوجه شود و نگاه کند. و
سقف است نه کف؛ این ردیف پیام مشتری را عیناً نگه می‌دارد و آن مالِ ما نیست که تا ابد بماند.

**چه چیزی ساخته نشد:** replay خودکار و alert، هر دو از چهار بند Codex. replay دکمه‌ای است
که هنوز هیچ‌کس یک بار هم لازمش نداشته و ساختنش یعنی حدس زدن اینکه چه کاری باید بکند —
جدول عمداً «ثبت» است نه «صف retry». alert جایی برای رفتن ندارد تا فاز B رصدپذیری؛ فعلاً
همان `console.error` است. بند سوم (جدا کردن خطای گذرا از شمارش) از قبل بسته بود: چرخه‌ای
که همه‌چیزش شکست، outage است و بخشیده می‌شود.

روش: فایل قبلش `nginx.conf.bak-2026-08-18` گرفته شد، نسخهٔ جدید با `scp` رفت،


است. پیش‌پرواز دیپلویش انجام شد — `ENV_NAME=production` (یکی از چهار مقدار مجاز، پس گیت
fail-closed رد می‌شود)، `TEST_ACCESS_USER` ست نیست، `TRUSTED_PROXY_IP_HEADER` ست است، و
مهاجرت‌های `0022`/`0023` روی پروداکشن اجرا شده‌اند. هشت کامیت فاصله است و هیچ‌کدام متغیر
تازه‌ای نمی‌خواهند. **منتظر تصمیم Sam.**

### سفارشی که تحویل نشد، و جدولی که هفت ماه خالی ماند — ۲۰۲۶-۰۸-۱۸

`C-01`. بازتأیید مستقل روی همین شاخه، و یافته از خودِ گزارش بزرگ‌تر بود.

**آنچه گزارش گفته بود:** نتیجهٔ `deliverMirzabotVerifiedWebhook` در `emitVerifiedWebhook`
دور ریخته می‌شود. درست بود — `Promise<void>` بود و `{ok,error}` را می‌بلعید.

**آنچه گزارش ندیده بود، و شکل کار را عوض کرد:** جدول `webhook_deliveries` از مهاجرت `0004`
در اسکیما هست، **با دقیقاً ستون‌های یک outbox** — `attempt_count`, `next_attempt_at`,
`last_response_status`, و `status IN ('PENDING','DELIVERED','FAILED','DEAD')` — و **هیچ کدی
در `src/` هرگز یک ردیف در آن ننوشته بود.** فقط تست‌ها truncate‌اش می‌کردند و مهاجر اسمش را
می‌برد. پس این برش «ساختن outbox» نبود، «وصل‌کردن outboxی که از قبل طراحی شده بود» بود.

**سه چیز که عوض شد:**

۱. **صف در همان تراکنش.** ردیف `webhook_deliveries` به همان `db.batch([...])` اضافه شد که
claim را VERIFIED می‌کند. `id` از جفت (claim, tx) ساخته می‌شود، پس تکرار خودبه‌خود idempotent
است — یک سفارش هرگز دو بار برای تحویل فرستاده نمی‌شود.

۲. **پیک، با retry و مهلت.** `flushWebhookDeliveries` ردیف‌های موعدرسیده را برمی‌دارد،
می‌فرستد، و نتیجه را می‌نویسد؛ backoff از یک دقیقه دو برابر می‌شود تا سقف یک ساعت، و بعد از
۸ تلاش ردیف `DEAD` می‌شود به‌جای اینکه تا ابد تلاش کند. `fetch` حالا `AbortSignal.timeout`
دارد — نداشت، و این sweep داخل همان درخواستی اجرا می‌شود که SMS بانکی را می‌بلعد.

۳. **`AUTO_FULFILLMENT_ENABLED` شد تصمیم اجباری** (`MUST_BE_DECIDED`) — همان‌جا که
`MIRZABOT_INTEGRATION_ENABLED` و `AUTO_MATCH_ENABLED` نشسته‌اند. و پیام خطا دیگر یک جملهٔ
مشترک نیست: هر سوییچ **عاقبت خودش** را می‌گوید، چون جملهٔ مشترک برای دوتای دیگر دروغ بود.

**دو بار تست خودم را رد کرد — و این مهم‌ترین بخش است:**

- اول پنج تست نوشتم که همه سبز بودند. بعد کد را به شکل باگ برگرداندم (insert **بعد** از
  batch به‌جای داخلش) و **هر ۱۴ تست سبز ماندند.** یعنی هیچ‌کدام خاصیت تراکنشی را نمی‌سنجید.
  تست واقعی این شد: یک `CHECK` موقت روی جدول که نوشتن آن ردیف را رد می‌کند — و ادعا اینکه
  آن‌وقت **claim اصلاً VERIFIED نشود**. با کد درست سبز است؛ با insert بیرون از batch، و فقط
  آن یکی، قرمز.
- در `flushWebhookDeliveries` کامنت نوشته بودم که `FOR UPDATE SKIP LOCKED` جلوی دو sweeper
  هم‌زمان را می‌گیرد. برداشتمش: **هیچ تستی متوجه نشد.** نگهبان واقعی *lease* است — همان
  `UPDATE` که ردیف را می‌خواند `next_attempt_at` را جلو می‌برد. برداشتن lease تست هم‌زمانی را
  می‌خواباند. کامنت اصلاح شد تا فقط چیزی را ادعا کند که ثابت شده. **قاعدهٔ ۶ روی کامنت‌های
  خودم هم صدق می‌کند.**

**یک اصلاح جانبی:** `matchId` یک UUID تازه بود، ولی upsert روی جفت (tx, claim) کلید می‌خورد و
`id` را overwrite نمی‌کند — پس اگر ردیفی از قبل بود، شناسه‌ای که در payload و در snapshot
بازگردانی می‌نشست به ردیفی اشاره می‌کرد که وجود نداشت. حالا اول خوانده می‌شود.

**وضعیت امروز روی پروداکشن:** این مسیر **خاموش است** — `AUTO_FULFILLMENT_ENABLED` و
`MIRZABOT_WEBHOOK_URL` روی سرویس ingest ست نیستند (خوانده‌شده از Coolify API، ۰۸-۱۸). پس
هیچ سفارشی تا امروز از این راه گم نشده. **ولی از این کامیت به بعد، ingest بدون تصمیم صریح
روی این سوییچ در production بالا نمی‌آید** — پس قبل از دیپلوی بعدیِ ingest باید
`AUTO_FULFILLMENT_ENABLED` (فعلاً `false`) در Coolify ست شود، وگرنه کانتینر بالا نمی‌آید.
این عمدی است و همان fail-closed خواسته‌شده است.

### یک poller به ازای هر توکن — ۲۰۲۶-۰۸-۱۸

از بازبینی بیرونی (`M-06`). `apps/bot/src/singleton.ts`.

تلگرام دقیقاً یک `getUpdates` به ازای هر توکن اجازه می‌دهد؛ دومی `409` می‌گیرد. این علامت
از قبل در همین سند به‌عنوان یک ردیف عیب‌یابی بود — چون روی لپ‌تاپ وقتی پروسهٔ قبلی یتیم
می‌ماند اتفاق می‌افتد. **روی سرور اتفاق نیست، شکلِ عادیِ دیپلوی است:** Coolify کانتینر تازه
را قبل از خواباندن قدیمی بالا می‌آورد.

۴۰۹ها نیمهٔ دیدنی‌اند. نیمهٔ نادیدنی بدتر است: `getUpdates` هر آپدیت را به همان کسی می‌دهد
که پرسیده، پس در آن پنجره بعضی فشارهای مشتری‌ها به کانتینری می‌رود که دارد کشته می‌شود.
چیزی گم نمی‌شود — `telegram_updates` هر آپدیت را دقیقاً یک بار claim می‌کند — ولی **فرضِ
«ربات تنها نویسنده است» می‌شکند**، و همان مسابقه‌هایی که این هفته بستیم (`0022`, `0023`)
یک‌جا قابل دسترس می‌شوند.

**درمان:** یک `pg_advisory_lock` در سطح **session**، روی **کانکشن اختصاصی خودش**، برای تمام
عمر پروسه. کلیدش از **توکن** ساخته می‌شود نه از یک ثابت — ربات تست و ربات پروداکشن در دوران
گذار روی یک دیتابیس‌اند و نباید هم را ببندند. خودِ توکن از این فایل بیرون نمی‌رود؛ فقط hashش
آن هم به شکل دو عدد صحیح.

**منتظر می‌ماند، نه اینکه بمیرد.** پنجرهٔ rolling deploy خودش در چند ثانیه بسته می‌شود، و
پروسه‌ای که تسلیم شود فروشگاه را بی‌ربات می‌گذارد در حالی که دیپلوی «موفق» گزارش شده.
قبلش در لاگ می‌گوید، چون پروسه‌ای که بی‌صدا پشت یک قفل ایستاده از یک پروسهٔ هنگ‌کرده
قابل تشخیص نیست.

**و چیزی که فقط با تست پیدا شد:** اگر همان کانکشن بمیرد، قفل هم می‌میرد — Postgres با رفتن
سوکت آزادش می‌کند. بی‌هندلر، خطای `error` پروسه را می‌کشت (نتیجهٔ درست به دلیل غلط). با
هندلرِ خالی، ربات **بدون داشتن قفل به poll ادامه می‌داد** و یک poller دوم می‌توانست کنارش
بالا بیاید — دقیقاً همان چیزی که این فایل برای جلوگیری از آن هست، و کاملاً بی‌صدا. حالا به
فراخوان داده می‌شود و `server.ts` پروسه را می‌بندد؛ کانتینر برمی‌گردد و قفل را دوباره
می‌گیرد.

**و در همان برش، `M-07`:** probe ربات در `Dockerfile` برای هرچه ingest/dashboard نبود
`process.exit(0)` می‌زد — کامنت خودش صادقانه می‌گفت «فقط ثابت می‌کند PID 1 زنده است، که
داکر از قبل می‌دانست». آن حرف وقتی درست بود که تنها خرابیِ جالبِ ربات **خارج‌شدن** باشد.
حالا نیست: **هر خرابیِ امروزِ ربات با پروسهٔ زنده اتفاق می‌افتد** — چرخه‌ای که روی یک
درخواست گیر کرده، Postgres در دسترس نیست و هر چرخه throw می‌کند، یا (از همین برش) poller‌ی
که منتظر آزادشدن توکن است. در هر سه، کانتینر بالاست و هیچ مشتری‌ای جواب نمی‌گیرد.

حالا حلقه یک بار در هر **چرخهٔ کامل** یک فایل را لمس می‌کند و probe سنش را می‌سنجد (۹۰
ثانیه = سه poll بیست‌وپنج ثانیه‌ای به‌علاوهٔ حاشیه؛ با `retries=3` یعنی حدود چهار دقیقه و
نیم سکوت تا ناسالم اعلام شود). **بعد** از چرخه، نه قبلش — چرخه‌ای که throw کرد و backoff
زد هنوز «حلقه می‌چرخد» است؛ چیزی که نباید سالم گزارش شود چرخه‌ای است که **برنمی‌گردد**، و
دقیقاً همان است که liveness روی PID 1 نمی‌بیند. فایل، نه ردیف دیتابیس: سوال «سلامتِ **این**
کانتینر» است، و ردیفی که برای خواندنش باید به دیتابیس رسید یکی از همان چیزهایی را فرض
می‌گیرد که دارد سنجیده می‌شود.

**سنجش با برداشتن نگهبان:** با تبدیل `pg_try_advisory_lock` به `SELECT true`، **۴ تست از ۵**
قرمز می‌شوند. برخلاف مسابقه‌های HTTP، این یکی **قطعی** است: دو کانکشن یا هر دو قفل دارند یا
ندارند، و Postgres تصمیم می‌گیرد نه حلقهٔ رویداد. مرگِ کانکشن هم با
`pg_terminate_backend` سنجیده می‌شود — یعنی دقیقاً همان چیزی که `kill -9` و
`docker stop` از دید Postgres‌اند.

### یک دستگاه، یک توکن زنده — و ده `catch` که از اول کار نمی‌کردند — ۲۰۲۶-۰۸-۱۸

از بازبینی بیرونی (`H-04`). مهاجرت **`0023_one_active_credential_per_device.sql`**.

هر سه مسیر اعتبارنامه ردیف `ACTIVE` را می‌خواندند و بعد می‌نوشتند. دو فراخوان هم‌زمان یعنی
**دو توکن فعال برای یک گوشی**، و هزینه‌اش سه چیز است:

- **باطل‌کردن، یکی را باطل می‌کند و دیگری کار می‌کند.** اپراتوری که گوشی گم‌شده را تازه قطع
  کرده، قطع نکرده.
- داشبورد هرکدام که `LIMIT 1` برگرداند نشان می‌دهد، **بدون هیچ ترتیبی**.
- `findActiveCredentialByPrefix` هم `LIMIT 1` دارد — پس با دو ردیف هم‌پیشوند، **جوابِ احراز
  هویت به پلنی بند است که Postgres انتخاب کرده.** احراز هویتی که قطعی نیست، احراز هویتی است
  که نمی‌شود درباره‌اش استدلال کرد.

`revoke` هم از `WHERE id = ?` به `WHERE device_id = ? AND status = 'ACTIVE'` رفت — تنها
کاری که کل هدفش این است که «بعدش هیچ‌چیز کار نکند» نباید یکی را جا بگذارد.

**و یافتهٔ گران‌تر، که سرِ راه پیدا شد:** برای برگرداندن ۴۰۹ به‌جای ۵۰۰ دنبال الگوی موجود
گشتم و دیدم **ده `catch` در داشبورد** این را می‌پرسند:

```ts
if (String(e).includes('UNIQUE')) ...
```

این جملهٔ SQLite است (`UNIQUE constraint failed: t.c`). **Postgres این را نمی‌گوید** —
می‌گوید `duplicate key value violates unique constraint "t_pkey"`، با حروف کوچک. سنجیده شد
روی درایور واقعی: `includes('UNIQUE')` برابر **`false`** است. یعنی از روزِ انتقال به Postgres،
هر کدام از آن ده جا **۵۰۰ برمی‌گرداند جایی که ۴۰۹ منظورش بوده**. آن‌هایی که اسم ایندکس را هم
دستی چک می‌کردند کار می‌کردند — و دقیقاً به همین دلیل کسی بقیه را ندید.

درمان یک تابع در `packages/db` است: `isUniqueViolation(err)` روی `SQLSTATE 23505` —
همان‌جایی که CLAUDE.md می‌گوید تفاوت SQLite و Postgres باید یک بار حل شود، نه ده بار.
تستش خطا را از **خودِ درایور** می‌گیرد نه از یک fixture، و صریحاً ادعا می‌کند که رشتهٔ قدیمی
آن را **نمی‌بیند** — چون کامنت بود که گذاشت این باگ زنده بماند.

**سنجش با برداشتن نگهبان — و چیزی که ثابت نشد:** با drop کردن ایندکس، **هر ۲۷ تست دستگاه سبز
ماندند.** دو `app.fetch` هم‌زمان در یک پروسه را نمی‌شود مجبور کرد دقیقاً روی همان دستور
درهم بروند؛ هندلرها پشت سر هم تمام می‌شوند و خواندنِ دومی ردیف اولی را می‌بیند. پس تضمین
جایی اثبات شد که **می‌شود**: دو `INSERT` در `verify_invariants.sql` (حالا **۳۰** ادعا)، که
قطعی است و لحظه‌ای که ایندکس نباشد قرمز می‌شود. تست‌های هم‌زمانیِ هندلر می‌مانند ولی
**قراردادِ مسیر** را نگه می‌دارند نه تضمین را، و کامنت خودشان همین را می‌گوید — چون تستی که
ادعا کند چیزی را ثابت کرده و نکرده باشد، از نبودنش بدتر است.

### یک سفارش، یک چک‌اوت باز — ۲۰۲۶-۰۸-۱۸

از بازبینی بیرونی (`H-05`)، بازتأییدشده روی همین شاخه. مهاجرت **`0022_one_open_payment_per_order.sql`**.

`checkoutFor` پرداخت باز سفارش را می‌خواند، چیزی پیدا نمی‌کند، یک کارت می‌چرخاند و درج
می‌کند. **خواندن، بعد نوشتن** — پس دو فراخوان هم‌زمان هر دو هیچ نمی‌بینند و هر دو درج
می‌کنند.

آنچه از دست می‌رود ردیف تکراری نیست؛ **دو شمارهٔ کارت متفاوت روی یک سفارش** است. مشتری به
کارتی که روی صفحه‌اش است پول می‌فرستد، `recordPaidClick` claim را روی **جدیدترین** باز
می‌کند، و تایید خودکار جفت را رد می‌کند چون حساب یکی نیست (شرط ۵). پول واقعی، رسید درست،
و پرداختی که برای همیشه در صف بررسی دستی می‌ماند.

کامنت خودِ تابع می‌گوید «عمداً idempotent» — و هست، **در برابر یک فراخوان در لحظه**. حلقهٔ
poll ربات یک فراخوان در لحظه است، پس این هرگز شلیک نکرده. ولی این خاصیتِ رانتایمِ امروز
است نه خاصیتِ دیتا، و روزی که نویسندهٔ دوم پیدا شود (پنل، وبهوک، rolling deploy با دو
poller) کامنت همچنان درست می‌ماند و تضمین نه. همان استدلال `0016`، یک وضعیت زودتر.

`INSERT` حالا `ON CONFLICT (order_id) WHERE ... DO NOTHING` دارد و بازنده ردیف برنده را
می‌خواند، پس هر دو با **همان** کارت بیرون می‌آیند. برای مشتری این یعنی یک چک‌اوت که دو بار
کشیده شده — همان حالت عادی رفت‌وبرگشت بین صفحه‌ها.

**سنجیده‌شده قبل از نوشتن، با حقیقت بیرونی نه با این فایل:** دامپ ۰۸-۱۱ (۴٬۶۲۹ پرداخت) صفر
سفارش با بیش از یک ردیف `Unpaid`/`waiting` دارد — شمرده با `COLLATE utf8mb4_bin`، وگرنه
MySQL بزرگی حروف را نادیده می‌گیرد (قاعدهٔ ۷). سیم هم صفر. مهاجرت بدون خطا اعمال شد.

**سنجش با برداشتن نگهبان — و آنچه بار اول واقعاً ثابت نشد:** تست مسابقه اول سبز بود ولی
**نگهبان را صدا نمی‌زد.** `rotateCard` ردیف را `FOR UPDATE SKIP LOCKED` برمی‌دارد، و فیکسچر
فقط **یک** کارت ACTIVE دارد — پس فراخوان دوم قبل از رسیدن به `INSERT` با دست خالی برمی‌گشت و
مسابقه روی قفلِ کارت حل می‌شد، نه روی ایندکس. (همین باعث شد در اجرای کامل قرمز شود، چون
زمان‌بندی فرق کرد.) حالا تست خودش یک کارت ACTIVE دوم می‌سازد، پس هر دو به درج می‌رسند. با
**برداشتن ایندکس و `ON CONFLICT` هر دو** — یعنی دقیقاً حالت قبل — تست می‌گوید
`expected 2 to be 1` و بقیه سبز می‌مانند.

**دو ادعای تازه در `verify_invariants.sql`** (حالا **۲۸** ادعا): دو چک‌اوت باز رد می‌شود، و
رد شدنش بین دو وضعیتِ باز هم برقرار است.

**و `M-09` که همین‌جا خودش را نشان داد:** اجرای `verify_invariants` روی سیمِ seed‌شده قبل از
**اولین** ادعا با `users_telegram_id_key` می‌مرد — چون شناسهٔ فیکسچرش `900000001` بود و
فیکسچر فروشگاه همان دو عدد را برداشته بود. سرصفحهٔ همان فایل ادعا می‌کرد «روی هر محیطی، پر
یا خالی، امن است». حالا شناسه‌ها **منفی**اند: تلگرام هرگز شناسهٔ منفی نداده، پس این یک
namespace است نه یک پیشوندِ امیدوارانه.

**یک حد که ثبت می‌شود:** دفتر اسکیما می‌گوید «به‌روز» چون فایل اجرا شده — نه چون شکل دیتابیس
درست است. وقتی همین ایندکس را دستی drop کردم، `schema status` همچنان «current» گفت.
دفتر تاریخچهٔ اجراست؛ چیزی که **شکل** را می‌سنجد `verify_invariants.sql` است. هر دو لازم‌اند.

### بدنه، قبل از اینکه در حافظه باشد، شمرده می‌شود — ۲۰۲۶-۰۸-۱۸

از بازبینی بیرونی (`H-02`)، بازتأییدشده روی همین شاخه. هر دو مسیر عمومی اول تخصیص می‌دادند و
بعد اندازه می‌گرفتند:

| کجا | چه بود |
| --- | --- |
| `POST /api/v1/sms` | `Content-Length` **فقط وقتی موجود بود** چک می‌شد — پس یک درخواست chunked کلاً از چک رد می‌شد |
| همان‌جا | بعدش `c.req.json()` هرچه رسیده بود را parse می‌کرد؛ تخصیص **قبل** از اندازه‌گیری |
| همان‌جا | چک دوم بعد از parse روی `JSON.stringify(body).length` بود — که واحد UTF-16 می‌شمارد. یک پیامک فارسی در UTF-8 دو بایت به ازای هر کاراکتر است و این‌جا یک واحد، پس عددی که با سقفی به اسم `_BYTES` مقایسه می‌شد **تقریباً نصف بایت‌ها** بود |
| `INGEST_MAX_BODY_BYTES` | با `parseInt` خوانده می‌شد و `NaN` بررسی نمی‌شد. `n > NaN` همیشه false است — پس یک غلط تایپی مثل `8kb` سقف را **گشاد نمی‌کرد، برمی‌داشت** |
| `POST .../mirzabot/claims` | کل بدنه با `c.req.text()` **قبل از احراز هویت** خوانده می‌شد (HMAC روی بایت خام است، پس ناگزیر)، بدون هیچ سقف و هیچ rate limit |

**درمان:** `bodyLimit` خودِ Hono روی هر دو مسیر — پلهٔ پنجم نردبان، وابستگی از قبل نصب است.
`Content-Length` اعلام‌شدهٔ بزرگ‌تر از سقف مستقیم رد می‌شود، و بدنهٔ chunked **حین جریان**
شمرده و وسط راه قطع می‌شود. سقف مسیر claims جداگانه و کوچک‌تر است (۴ کیلوبایت؛ بدنه‌اش
دوازده فیلد کوتاه است) و همان limit IP را هم گرفت. `INGEST_MAX_BODY_BYTES` حالا موقع بالا
آمدن اعتبارسنجی می‌شود، و چکِ کاراکتریِ بعد از parse حذف شد چون هم زائد بود هم غلط.

**و باگی که فقط با اجرا پیدا شد — و درسش از خودش بزرگ‌تر است:** بعد از وصل‌کردن میدل‌ور،
تست‌ها هنوز به‌جای ۴۱۳ جواب **۴۰۰** می‌گرفتند. علت: `bodyLimit` بدنهٔ بزرگ را با
**خطا‌دادن به استریم** اعلام می‌کند، و هندلر `c.req.json()` را داخل `try/catch` داشت — پس
سیگنالِ میدل‌ور را می‌بلعید و `bad_json` برمی‌گرداند. **یک `catch` عریض، سیگنالِ یکی دیگر را
به خطای خودت تبدیل می‌کند.** حالا اول `text()` بیرون از try خوانده می‌شود و فقط `JSON.parse`
گارد دارد.

**سنجش با برداشتن نگهبان:** بدون میدل‌ور **۷ تست قرمز** (شامل یک تست قدیمی که از قبل بود)،
۹۲ سبز. بدون اعتبارسنجی `INGEST_MAX_BODY_BYTES` و بدون limit مسیر claims → دقیقاً **۲ تای
دیگر**.

**آنچه ادعا نمی‌شود:** `Content-Length` دروغین این‌جا سوراخ نیست چون پارسر HTTP خودِ Node
دقیقاً همان تعداد بایتِ اعلام‌شده را به درخواست می‌دهد — ولی این را **در تست ثابت نکرده‌ام**،
چون تست واحد پارسر Node را رد می‌کند. مسیر chunked که واقعاً باز بود، ثابت شده است.

### کلید rate limit هدری بود که دیگر وجود ندارد — ۲۰۲۶-۰۸-۱۸

از بازبینی بیرونی (`H-03` و `M-01`)، بازتأییدشده روی همین شاخه.

تنها سطح عمومی پلتفرم این را می‌نوشت:

```ts
const ipKey = c.req.header('cf-connecting-ip') ?? 'unknown';
```

Cloudflare ۰۸-۱۷ از مسیر بیرون رفت. یعنی این هدر **هرگز** نمی‌آید، و همین یک خط در **دو جهت
مخالف** شکسته است:

- **همه در یک سطل‌اند.** یک گوشی پرترافیک کل ناوگان را ۴۲۹ می‌کند، و محدودیت دیگر دربارهٔ
  هیچ‌کس خاصی حرف نمی‌زند.
- **هدر دست مهاجم است.** حالا هیچ‌چیز پاکش نمی‌کند، پس کلاینتی که *بفرستدش* سطل خودش را
  انتخاب می‌کند و می‌تواند هر درخواست عوضش کند — یعنی محدودیت با تایپ‌کردن یک اسم هدر دور
  می‌خورد.

limiter‌ای که هم بی‌گناه را جریمه می‌کند و هم گناهکار را رد می‌کند، از نبودنش بدتر است، چون
شبیه محافظت است.

**درمان:** `clientIp` در `packages/domain/src/rateLimit.ts`. هدرِ حاملِ آدرس **از پیکربندی
نام می‌گیرد** (`TRUSTED_PROXY_IP_HEADER`)، نه از حدس — چون اعتماد به یک هدر یعنی اعتماد به هر
کسی که می‌تواند ستش کند، و فقط اپراتور می‌داند پروکسی کدام را **overwrite** می‌کند.
پاسخ وقتی هدر نامگذاری‌نشده یا غایب است `null` است، و فراخوان‌ها آن‌وقت limitِ IP را
**رد می‌کنند، نه اینکه همه را در یک سطل بگذارند.**

`X-Real-IP` گزینهٔ درست است چون nginx با `$remote_addr` رویش می‌نویسد. `X-Forwarded-For`
پیش‌فرضِ غلط است: nginx به آن **اضافه** می‌کند، پس مقدارِ ساختهٔ کلاینت در رشته می‌ماند.

**limiter ورود (`M-01`)** — قفلِ حسابیِ موجود (۵ تلاش، ۱۵ دقیقه) دو حمله را نمی‌بیند:

- **هزینه.** هر تلاش scrypt اجرا می‌کند، و برای آدرس ناموجود هم عمداً همان هزینه پرداخت
  می‌شود تا نشود فهمید کدام آدرس واقعی است. همان زمانِ ثابت اهرم مهاجم است: آدرس‌های
  ساختگی هیچ ردیفی ندارند که قفل رویش بشمارد.
- **انکار سرویس.** پنج حدس غلط هر ۱۵ دقیقه یک اپراتور واقعی را دائماً بیرون نگه می‌دارد،
  و حدس‌زننده به هیچ رمزی نیاز ندارد.

پس دو پنجرهٔ ثابت در حافظه، **قبل از هر hashی**: ۲۰ در دقیقه به ازای هر IP (وقتی IP معلوم
باشد) و ۱۲۰ در دقیقه سراسری. سراسری خیلی بالاتر از هر مصرف واقعی است — سقفِ سوءاستفاده،
نه محدودیتِ استفاده.

**و همان `clientIp` روی ثبت IP نشست هم اعمال شد.** قبلاً `cf-connecting-ip` بعد
`x-forwarded-for` بود — هر دو کاملاً قابل جعل. «نشست‌های من» آدرسی را نشان می‌داد که
**بازدیدکننده انتخابش کرده بود**، که از نشان‌ندادن بدتر است: اپراتوری که می‌خواهد ببیند
حسابش از کجا استفاده شده، داستانِ مهاجم را به‌عنوان شاهد می‌خواند.

**سنجش با برداشتن نگهبان — و یک درس از خودِ سنجش:** اولین باری که `clientIp` را به رفتار
قدیمی برگرداندم، تست یکپارچگی «نمی‌شود با هدر خودمان دورش زد» **سبز ماند**. چون فقط ادعا
می‌کرد هر درخواست ۴۰۱ می‌گیرد — که با سطل تازه هم درست است. تست بازنویسی شد: `x-real-ip`
ثابت (یک مهاجم) ولی `cf-connecting-ip` و `x-forwarded-for` چرخان؛ حالا با کد قدیمی
**۴ تست قرمز و ۲۵ سبز** می‌شوند. دقیقاً همان قاعدهٔ ۶، این‌بار روی تستِ خودم.

**نیمه‌ای که کد نیست و دست Sam است:** یک خط در `/root/shikoo-tls/nginx.conf` داخل هر
`location`:

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

و بعد `TRUSTED_PROXY_IP_HEADER=X-Real-IP` روی هر دو اپلیکیشن در Coolify. تا وقتی هر دو نیمه
انجام نشده limitِ IP خاموش است — و ingest موقع بالا آمدن همین را در لاگ می‌گوید.

### `ENV_NAME` دیگر حدس نیست — ۲۰۲۶-۰۸-۱۸

از بازبینی بیرونی (`C-02`)، بازتأییدشده روی همین شاخه.

`ENV_NAME` را هر دو سرویس این‌طور می‌خواندند: `process.env.ENV_NAME ?? 'local'`. یعنی
`prod`، `Production`، مقدار با فاصلهٔ آخر، و **نگذاشتنش** همه «local» می‌شدند. و «local» یعنی:

- گذر از ورود (`TEST_ACCESS_USER`) فعال می‌ماند
- درخواست تغییردهنده **بدون هیچ `Origin`** پذیرفته می‌شود — و این تنها جایگزین توکن CSRF است
- کوکی نشست ممکن است بدون `Secure` صادر شود
- ingest دیگر اصرار نمی‌کند که دو سوییچِ «آیا پول اصلاً تایید می‌شود» تصمیم‌گیری شده باشند

هر چهارتا fail-open‌اند و هر چهارتا روی **یک غلط تایپی** در متغیری می‌چرخند که بعد از اولین
دیپلوی کسی نمی‌خواندش.

**درمان، در `packages/contracts/src/env.ts`:**

- `ENV_NAME` یک enum چهارتایی است — `local` · `test` · `staging` · `production` — و
  **پیش‌فرض ندارد**. غایب یا ناشناخته یعنی پروسه بالا نمی‌آید. راهی برای پرسیدن «آیا من
  دیپلوی شده‌ام؟» وجود ندارد که خودش به همین متغیر بند نباشد، پس به‌جای حدس، هر پروسه
  می‌گوید کجاست.
- مقدارِ parse‌شده **تایپ اتحادی** است، نه رشته. مقایسه با `'prod'` دیگر **کامپایل نمی‌شود** —
  چک زمان اجرا محیط را می‌گیرد، تایپ نفر بعدی را.
- هر سه مصرف‌کننده از `!== 'production'` به **allowlist** (`isRelaxedEnv`) رفتند. آن مقایسه
  به staging اجازهٔ همه‌چیز می‌داد؛ یک staging روی اینترنت با ورودِ ردشده دقیقاً همان چیزی
  است که گارد پروداکشن برای جلوگیری از آن هست. نگهبان سیدر (`assertLocal`) هم همین شد —
  قبلاً `prod` و `staging` از تنها گاردی که از تونل SSH جان به در می‌برد رد می‌شدند.

**سنجش با برداشتن نگهبان، دو بار:** با برگرداندن `parseEnvName` به پیش‌فرض `local` دقیقاً دو
تست قرمز شدند و ۱۷ تای دیگر سبز ماندند؛ با برگرداندن `isRelaxedEnv` به `!== 'production'`
دقیقاً دو تای **دیگر**. یعنی هر نگهبان تست خودش را دارد.

**هزینه‌اش، صریح:** `ENV_NAME` حالا برای اجرای دستی سرویس‌ها هم لازم است. دستورهای
[راه‌اندازی](#راهاندازی-و-اجرا) و `deploy/README.md` به‌روز شدند و `playwright.config.ts`
هم آن را می‌دهد. `seed:sim` استثناست: unset همچنان می‌گذرد، چون دو گارد دیگرش — میزبان محلی
و شمار کاربر زیر هزار — همان حالت را می‌پوشانند.

**و یک اشکال محیطی که سر همین اجرا پیدا شد:** Playwright وقتی روی شل با
`HTTP_PROXY=http://127.0.0.1:10808` (حالت عادی این ماشین) اجرا شود، سلامت‌سنجی سرورهای
loopback را **از پروکسی** می‌پرسد و ۵۰۳ می‌گیرد — حتی قبل از اینکه سروری بالا بیاید. خطایش
«Timed out waiting from config.webServer» است در حالی که یک خط بالاتر نوشته
`dashboard listening`. حالا کانفیگ خودش loopback را از پروکسی بیرون می‌گذارد.

### دفتر اسکیما — ۲۰۲۶-۰۸-۱۸

بدهی بازِ برشِ لبه بسته شد: **دیتابیس حالا خودش می‌گوید کدام مهاجرت‌ها را دیده.**

`packages/db/src/schema.ts` یک جدول `schema_migrations` می‌سازد — یک ردیف به ازای هر فایل
اعمال‌شده، با `sha256` همان چیزی که واقعاً اجرا شد. سه حالت از همین یک ستون بیرون می‌آید و هر
سه خرابی‌هایی‌اند که وگرنه فقط با خواندن دستی پروداکشن پیدا می‌شوند:

| | |
| --- | --- |
| **pending** | فایلی روی دیسک بدون ردیف — دقیقاً باگ ۰۸-۱۷ |
| **drift** | ردیفی که checksumش دیگر نمی‌خواند. ویرایش یک مهاجرتِ اعمال‌شده همان‌جایی است که دو دیتابیس بی‌صدا از هم جدا می‌شوند |
| **unknown** | ردیفی بدون فایل — دیتابیس از این checkout جلوتر است. برگرداندن کد بدون برگرداندن اسکیما یک دیپلوی واقعی است و باید صدا بدهد |

```bash
corepack pnpm --filter @shikoo/db schema status                  # خروجی ۰ یعنی به‌روز، ۱ یعنی نه
corepack pnpm --filter @shikoo/db schema up                      # هرچه مانده، به ترتیب
corepack pnpm --filter @shikoo/db schema baseline 0021_operator_auth.sql
```

**چهار تصمیم که عمدی‌اند:**

- **همه‌چیز زیر یک `pg_advisory_lock`** (`SCHEMA_LOCK_ID = 8152026`). دو replica که هم‌زمان
  دیپلوی می‌شوند نمی‌توانند هر دو `0022` را اجرا کنند. با برداشتن قفل ثابت شد: دقیقاً همان یک
  تست قرمز شد و ۵۳ تای دیگر سبز ماندند.
- **هر فایل تراکنش خودش، با ردیف دفتر داخل همان تراکنش.** اجرایی که وسط راه می‌میرد،
  فایل‌های تمام‌شده را ثبت‌شده می‌گذارد؛ اجرای بعدی ادامه می‌دهد نه از اول.
- **`baseline` برای دیتابیسی که از دفتر قدیمی‌تر است.** پروداکشن هر ۲۱ مهاجرت را دارد و
  هیچ ردیفی ندارد؛ `up` آن‌جا به‌جای تلاش برای `CREATE TABLE users` **می‌ایستد** و اسم
  `baseline` را می‌برد. سنجهٔ «آیا اسکیما از قبل هست» عمداً `to_regclass('users')` بدون
  پیشوند است — نسخهٔ `public.users` به `search_path` گوش نمی‌داد و هر تست را روی اسکیمای
  اسکرچ با جدول‌های سیم جواب می‌داد.
- **`schema_migrations` در `KEEP` سیدر است.** اولین `seed:sim` بعد از این برش دفتر را
  truncate کرد و `status` روی دیتابیسی که هر ۲۱ را داشت گفت «۲۱ تا مانده». دفتری که دروغ
  می‌گوید از نبودنش بدتر است.

۱۲ تست روی Postgres واقعی، هرکدام در اسکیمای اسکرچ خودش (`packages/db/test/schema.test.ts`).
CLI هم روی سیم در **همان وضعیت پروداکشن** اجرا شد: اسکیما هست، دفتر خالی → `status` کد ۱،
`up` رد کرد، `baseline 0021_operator_auth.sql` بیست‌ویک ردیف نوشت، بعد `schema is current`.

**بدهی باز:** روی پروداکشن هنوز baseline نشده، و هیچ سرویسی موقع بالا آمدن `status` را چک
نمی‌کند — یعنی درز کد/اسکیما هنوز می‌تواند دیپلوی شود، فقط دیگر نامرئی نیست.

### دو پرچم قدیمی که رشته خوانده می‌شدند — ۲۰۲۶-۰۸-۱۸

از گزارش Codex (`H-01`)، سنجیده و اندازه‌گیری‌شده روی هر ۱۱٬۲۴۱ ردیف واقعی.

مهاجرت `user.roll_Status` را با `t.bool(r.roll_Status)` می‌خواند که برای رشته نوشته شده بود؛
ولی **mysql2 یک `tinyint(1)` را عدد برمی‌گرداند، نه رشته**. پس `0` و `1` هر دو truthy
می‌شدند و **هر ۱۱٬۲۴۱ مشتری با «قوانین را پذیرفته» منتقل می‌شدند**. اندازه‌گیری واقعی:
۱۱٬۲۴۱ → **۱۰٬۲۷۸** پذیرفته، یعنی **۹۶۳ نفر** گیت قوانین را که هرگز ندیده بودند پس می‌گیرند.

مورد دومی که گزارش ندیده بود: `reagent_report.get_gift` دقیقاً همان اشتباه را داشت — پاداش
معرفی برای همه «قبلاً گرفته‌شده» ثبت می‌شد.

درمان `t.legacyBool(value, field)` است که دامنه را صریح می‌شمارد (`0`/`1`، `"0"`/`"1"`، `""`،
`NULL`) و **روی هر چیز دیگری خطا می‌دهد** — همان قاعدهٔ «هرگز fallback نگذار» که بقیهٔ
`transform.ts` دارد.

**و درسی که خودِ باگ نبود:** اولین تستی که برایش نوشتم `legacyBool` را می‌سنجید، نه نقطهٔ
فراخوانش — پس روی کدِ **درست‌نشده** هم سبز بود. شاهد واقعی حالا در `verify.ts` است: دو جفت
شمارش دو طرفه بین MySQL و Postgres که اگر پرچم غلط خوانده شود اختلاف می‌دهند.

**بدهی باز که همین‌جا صریح ثبت می‌شود:** تایپ `Row = Record<string, string | null>` در
`migrate.ts` **می‌داند که دروغ می‌گوید**. گشاد کردنش ۴۸ نقطه در ۱۴ تابع تبدیل را روشن
می‌کند؛ هر کدام باید جدا خوانده شود، نه با یک cast خاموش.

### لبه — ۲۰۲۶-۰۸-۱۷

**تصمیم Sam: Cloudflare کلاً برداشته شود، و ۸۰ و ۴۴۳ سرور دست‌نخورده بمانند.** هر دو رعایت شدند.

```
مرورگر ──▶ shikoo.mahamsteel.ir:9443 ──▶ shikoo-tls ──▶ dashboard:8788
           sms.mahamsteel.ir:9443    ──▶ (nginx در داکر) ──▶ ingest:8787
```

| | |
| --- | --- |
| DNS | هر دو `A` مستقیم به `164.132.198.184`، بدون پروکسی. صفر CNAME تونل |
| TLS | `shikoo-tls`، یک `nginx:alpine` روی شبکهٔ `coolify`، فقط `:9443` منتشر می‌کند · کانفیگ `/root/shikoo-tls/nginx.conf` |
| گواهی | Let's Encrypt، DNS-01 با `certbot-dns-cloudflare`، هر دو دامنه، `--cert-name shikoo` |
| تونل | **حذف شد** — نه سرویسی در Coolify، نه کانتینری |
| Access | از مسیر بیرون · متغیرهای مرده‌اش از کانتینر پاک شدند |

**چرا در کانتینر و نه روی nginx میزبان:** میزبان `:80` و `:2053` را برای دو سایت بی‌ربط
(`cdn-france`، `francestatus`) نگه داشته و قرار شد دست نخورد.

**و یک تصحیح که بخش ۳ پلن را بی‌دلیل ترسناک کرده بود:** این‌جا نوشته بود xray پورت `:443` را
گرفته. **غلط بود.** `ss -lntp` می‌گوید هیچ‌کس روی ۴۴۳ نیست؛ پنل زندهٔ مشتری‌ها روی پورت‌های
*جایگزین* کلادفلر است (۲۰۸۳، ۲۰۹۵، ۸۴۴۳، ۸۴۴۴، ۱۰۸۰). یعنی ۴۴۳ از کسی گرفته نمی‌شد.

#### سه چیزی که فقط با اجرا معلوم شد

**۱. نام کانتینر Coolify با هر دیپلوی عوض می‌شود — و پنل را خواباند.** قاعدهٔ ingress تونل به
`b8xibemxou4qhwmacxwzhws1-140750264380` اشاره می‌کرد؛ دیپلوی بعدی نامش را عوض کرد و
cloudflared گفت `dial tcp: lookup ... server misbehaving` و کلادفلر ۵۰۲ داد. **این نکته ماه‌ها
به‌عنوان یادداشت در همین سند بود** — یادداشتی که می‌گوید چیزی خواهد شکست تعمیر نیست.

درمانش `custom_network_aliases` است، **نه** `custom_docker_run_options`: مقدار
`--network-alias dashboard` در دومی نشسته بود و Coolify هرگز به داکر نداده بود. با فیلد درست و
یک دیپلوی، alias روی شبکه ظاهر می‌شود. حالا `dashboard` و `ingest` نام ثابت دارند، و یک دیپلوی
کامل با پاییدن ثابت شد که مسیر دیگر نمی‌شکند.

**۲. `proxy_set_header Host $http_host`، هرگز `$host`.** `originGuard` مقدار
`new URL(origin).host` را با `new URL(c.req.url).host` می‌سنجد و `URL.host` **پورت را نگه
می‌دارد**. `$host` پورت را می‌اندازد، پس هر درخواست تغییردهنده `cross_origin_forbidden`
می‌گرفت — همان باگ ۰۸-۱۶ (که سرِ scheme بود) با لباس تازه. سنجیده شد: مبدأ خودمان رد می‌شود،
مبدأ بیگانه هنوز رد می‌شود.

**۳. مهاجرت `0021` روی پروداکشن اجرا نشده بود.** کدِ ورود دیپلوی شده بود ولی اسکیما نه، پس
`POST /api/v1/auth/login` با `column "password_hash" does not exist` جواب ۵۰۰ می‌داد و
**هیچ‌کس نمی‌توانست وارد شود**. کسی ندید چون تا آن روز روی پروداکشن ورود امتحان نشده بود.
دیتابیس آن‌جا دفتر مهاجرت ندارد (`schema_meta` فقط پیکربندی است) — یعنی هیچ‌چیز درز بین کد و
اسکیما را صدادار نمی‌کند. **این بدهی روز بعد بسته شد** — بخش [دفتر اسکیما](#دفتر-اسکیما--۲۰۲۶-۰۸-۱۸).

#### بدهی‌های همین برش

- **توکن Cloudflare ۲۲ آگوست ۲۰۲۶ منقضی می‌شود، گواهی نوامبر تمدید می‌شود.** آن روز تمدید
  بی‌صدا شکست می‌خورد. یک توکن بدون انقضا با `Zone:DNS:Edit` لازم است.
- دو اپلیکیشن Access هنوز در پنل کلادفلر هستند — بی‌اثر، ولی پاک نشده‌اند.
- **`ufw` نصب نیست** و Sam برای دورهٔ تست نخواست، پس پنل Coolify روی `:8000` با HTTP ساده روی
  اینترنت باز است و توکن Rootش رمزنگاری‌نشده رد می‌شود.
- آدرس داخل اپ اندروید باید `https://sms.mahamsteel.ir:9443/api/v1/sms` شود. رله تا امروز
  هیچ‌وقت به پروداکشن چیزی نفرستاده — صفر رویداد، صفر دستگاه.
- پورت غیراستاندارد ممکن است روی بعضی شبکه‌های موبایل بسته باشد.
- **Cloudflare صفر نمی‌شود** تا وقتی ۸۰ و ۴۴۳ دست‌نخورده‌اند: DNS آن‌جاست و DNS-01 تنها راه
  گواهی است. صفرشدن یعنی یا انتقال DNS، یا آزادکردن ۴۴۳.

### دیپلوی — ۲۰۲۶-۰۸-۱۶

اولین باری که چیزی از این پروژه روی یک سرور واقعی بالا آمد.

| | |
| --- | --- |
| سرور | Ubuntu، **Coolify v4.3.4**. آدرسش عمداً این‌جا نیست — امروز پشت تونل مخفی است و این فایل کامیت می‌شود |
| Postgres | **۱۶.۱۵**، سالم · بکاپ شبانهٔ ۰۳:۰۰ · **یک بار واقعاً بازیابی شد** — ۶۲ جدول، ۲۶ invariant سبز. بکاپی که بازیابی نشده بکاپ نیست |
| سرویس‌ها | `shikoo-bot` (polling، بدون پورت) · `shikoo-ingest` سالم · `shikoo-dashboard` سالم · `shikoo-tunnel` بالا |
| دسترسی به تلگرام از سرور | سنجیده شد: `getMe` با توکن بی‌اعتبار **۴۰۱** برگرداند، یعنی مسیر باز است |

**سه چیزی که فقط با اجرا معلوم شد، نه با استدلال:**

- **`node:22-slim` نه `curl` دارد نه `wget`.** سلامت‌سنجی‌ای که Coolify خودش می‌سازد روی این
  ایمیج همیشه شکست می‌خورد و هر سه سرویس را unhealthy نشان می‌داد در حالی که هر سه سالم
  بودند. `HEALTHCHECK` حالا با `node -e` نوشته شده. داشبورد عمداً **۴۰۱ را هم سالم می‌شمارد**:
  بررسی از داخل کانتینر اجرا می‌شود، جایی که هیچ توکن Access وجود ندارد.
- **`originGuard` باید میزبان را بسنجد، نه origin را.** TLS در Cloudflare تمام می‌شود و تونل
  ساده forward می‌کند، پس `new URL(c.req.url).origin` می‌شود `http://…` در حالی که مرورگر
  `https://…` می‌فرستد. نتیجه: **هر نوشتنِ پنل `cross_origin_forbidden` می‌گرفت.** روی خودِ
  کانتینر اندازه‌گیری شد و علت دقیقاً و فقط طرح بود.
- **ورود با کد یک‌بارمصرف روی Zero Trust پیش‌فرض روشن نیست.** تنها روش موجود
  «Login with Cloudflare» بود با `restrict_to_account_members`, پس هر اپراتوری که عضو اکانت
  کلادفلر نبود «Authentication error» می‌گرفت. One-time PIN اضافه شد.

**نکته‌ای که در معماری می‌ماند:** نام کانتینرهای Coolify پایدار نیست — هر دیپلوی عوض می‌شود.
تا وقتی توپولوژی به یک فایل compose در مخزن منتقل نشده، هر اسکریپتی که نام کانتینر را
هاردکد کند بعد از دیپلوی بعدی می‌شکند.

### ورود با رمز، جای Cloudflare Access (۲۰۲۶-۰۸-۱۶)

**تصمیم Sam:** Access برداشته شود و پنل صفحهٔ ورود خودش را داشته باشد، با رمز و TOTP.

**و یک دلیل ساختاری که فقط حین کار پیدا شد:** تا وقتی Access هست **ادغام دو پنل ممکن نیست.**
هر پنل پشت یک اپلیکیشن Access با `aud` جدا بود و `access.ts` امضا را بر اساس مسیر می‌سنجید.
یک باندل که از یک مسیر سرو شود فقط یکی از آن دو توکن را دارد، پس نیمی از فراخوانی‌هایش
حتماً ۴۰۱ می‌گیرد — هر نیمی که باشد. پس ورود **قبل** از ادغام می‌آید، نه بعدش.

| | |
| --- | --- |
| مهاجرت | `0021_operator_auth.sql` — رمز، TOTP، قفل، و جدول `operator_sessions` |
| رمز | `scrypt` از `node:crypto`. argon2/bcrypt ماژول نیتیو‌اند و این مخزن یک ایمیج می‌سازد |
| TOTP | RFC 6238، سنجیده با **شش بردار رسمی خودِ RFC** |
| نشست | کوکی HttpOnly · فقط `sha256` توکن ذخیره می‌شود · ۱۲ ساعت بی‌کاری، سقف ۳۰ روز |
| قفل | ۵ تلاش، ۱۵ دقیقه — **داخل همان `UPDATE` که شمارش می‌کند** |
| ساخت اپراتور | `corepack pnpm --filter @shikoo/dashboard operator ...` — رمز از stdin، نه از آرگومان |

**آنچه این کار عوض می‌کند و باید صریح گفته شود:** Access یک لایهٔ هویت **جلوی** origin بود.
حالا صفحهٔ ورود ما تنها دیوار است. هر چیز غیرجذابی که در `operatorSession.ts` هست — قفل
داخل دستور، هش ساختگی برای ایمیل ناشناس، بررسی replay روی گام TOTP، ردیف audit روی هر رد
شدن — تفاوت بین یک صفحهٔ ورود و یک تشریفات است.

**سه نگهبان با برداشتن ثابت شدند:**

```
count-then-act به‌جای گارد در دستور  → «۵ حدس هم‌زمان» قرمز شد: ۳ شمرد، نه ۵
حذف بررسی گام TOTP                    → سبز ماند! گارد دوم (UPDATE شرطی) گرفتش
حذف هر دو                             → «همان کد دو بار» قرمز شد
حذف `revoked_at IS NULL`              → «نشست باطل‌شده» قرمز شد
```

دومی درس خودش را داشت: تست اول چیزی را ثابت نکرد چون **دو** نگهبان وجود داشت و من فقط
یکی را برداشته بودم. اگر همان‌جا می‌ایستادم، فکر می‌کردم بررسی گام لازم نیست.

**دو تستی که سبز بودند و چیزی ثابت نمی‌کردند:**

- `rerun-assignment.test.ts` ادعا می‌کرد «READ_ONLY رد می‌شود» ولی هویت را با هدر
  `cf-access-authenticated-user-email` می‌فرستاد — هدری که worker **هرگز نخوانده**. بازیگر
  واقعی `admin@example.com` بود که همان تست پاکش کرده بود، پس ۴۰۳ یعنی «چنین اپراتوری
  نیست»، نه «READ_ONLY اجازه ندارد».
- تست تازهٔ خودم برای صفحهٔ ورود اول با `new Response(...)` نوشته شد؛ آن سازنده در محیط
  تست پرتاب می‌کرد، پس پنل به مسیر «وارد نشده» می‌رفت و تست **به دلیل غلط** سبز می‌شد.

### تحویل روی پنل واقعی — و گروهی که حذف شده بود (۲۰۲۶-۰۸-۱۶)

زنجیرهٔ پول یک بار کامل روی پنل زندهٔ پاسارگاد اجرا شد: ساخت **۲۰۱**، لینک اشتراک **۹۸۰۰
بایت**، **۲۵ کانفیگ vless**، `DELETE` **۲۰۴** و تایید نبودن. تنها حلقه‌ای که هرگز تست نشده
بود، بسته شد.

**و همان‌جا یک چیز بیرون افتاد که هیچ تستی نمی‌توانست ببیند.** پیکربندی مهاجرت‌شده
`group_ids: [42, 2]` می‌فرستد و پنل جواب می‌دهد `404 "Group not found"`. گروه ۴۲ بعد از
دامپ ۲۰۲۶-۰۸-۱۱ از پنل حذف شده. `marzban.ts` این را **غیرقابل‌تکرار** می‌شمارد،
`provision.ts` سفارش را `FAILED` می‌کند، و `FAILED` در همان تراکنش کیف پول را برمی‌گرداند.

یعنی صبح اول بعد از سوئیچ، **هر خرید VIP شکست می‌خورد و جلوی چشم مشتری ریفاند می‌شد** —
و هیچ‌چیز در مخزن از قبل حرفی نمی‌زد. علت ساختاری است: پیکربندی ما یک عکس لحظه‌ای از پنلی
است که بدون ما عوض می‌شود.

**درمان: `panel:preflight`.**

```bash
DATABASE_URL=... PANEL_<CODE>=user:pass \
  corepack pnpm --filter @shikoo/bot panel:preflight
```

فقط-خواندنی: یک لاگین و دو `GET`. برای هر پلن فعالِ روی هر پنل فعال، گروه‌هایی را که یک
سفارش می‌فرستد با گروه‌هایی که پنل واقعاً دارد می‌سنجد. کد خروجی ۱ وقتی کسی باید نگاه کند.

دو تصمیم طراحی که ارزش نوشتن دارند:

- **به ازای هر پلن، نه هر پنل** — `planAttrs` روی `providerConfig` غلبه می‌کند، پس دو پلن روی
  یک پنل می‌توانند گروه‌های متفاوت بفرستند.
- **بدنه بازسازی نمی‌شود.** `groupIdsFor` در `marzban.ts` همان تابعی است که `provision`
  صدا می‌زند، پس آنچه سنجیده می‌شود همان است که فرستاده می‌شود. یک کپی دوم از آن قاعده با
  خودش سازگار می‌ماند و از کد جدا می‌افتد — دقیقاً قاعدهٔ ۶.

**اجرای واقعی روی دیتای مهاجرت‌شده (۲۰۲۶-۰۸-۱۶) ایستاد، و بیشتر از انتظار پیدا کرد:**

```
7e7a — سرویس VIP    panel has groups: 2, 83, 118, 119, 132, 133, 134
  ✗ ۷ پلن، هر هفت‌تا — sends [42,2], panel does not have [42]
4f24 · e9d5          ✓ همه [2]، موجود است
```

**هر هفت پلن VIP**، نه یکی. و یک قلم دوم که همان اجرا نشان داد: ردیف‌های مهاجرت‌شده املای
میراثی **`inbounds`** را دارند نه `group_ids`. اگر ابزار فقط `group_ids` را می‌خواند، برای
هر پنج پنل می‌گفت «چیزی نمی‌فرستد» و **هیچ‌چیز پیدا نمی‌کرد**.

سوال باز از ادمین کل: **گروه ۴۲ کِی و چرا حذف شد، و جایگزینش کدام است؟**

### ۲۰۲۶-۰۸-۱۴ (و) — کد تخفیف، و ۳۱ کدی که داشتند زنده می‌شدند

**مهم‌ترین چیز این برش کد ربات نیست، مهاجرت است.** جدول `discount_codes` از روی *ستون‌های*

| شرط PHP | ستون ما | تا امروز |

روی دامپ ۲۰۲۶-۰۸-۱۱ این گِردکردن نیست: از ۳۳ کد فروش، **۳۱ تا از قبل منقضی‌اند**، ۱۳ تا به

کدی که به محصول یا پنلِ حذف‌شده بسته است **وارد نمی‌شود** — بردنش بدون قیدش، قیدش را حفظ
نمی‌کند، بلکه به همه‌جا بازش می‌کند.

اجرای واقعی روی سیم: **۳۷ کد → ۱۹ ردیف** (۵ محصولِ رفته، ۳ پنلِ رفته، ۱۰ تکراری). از آن ۱۹

**دو جا عمداً از PHP سخت‌گیرترند:**

- `useuser` حذف شد. میراث اجازهٔ ۱، ۲، ۵ یا نامحدود بار به ازای هر مشتری می‌دهد؛ این‌جا
  `idx_redemption_once_per_user` یکتاست، پس **دقیقاً یک بار** و هیچ رقابتی نمی‌تواند دو
  ردیف بنویسد. جایگزینش شمارنده‌ای بود که دو تپِ هم‌زمان هر دو «یکی مانده» می‌خواندند.
- شمارش مصرف از **ردیف‌های redemption** است نه از ستون `usedDiscount` که PHP بعد از کار
  زیاد می‌کند و در پروداکشن با `Giftcodeconsumed` اختلاف دارد.

**تلهٔ سفارش دوم.** با تخفیف، تپِ دوم روی «ثبت سفارش» کد را مصرف‌شده می‌بیند، پلن را کامل
قیمت می‌زند، و **سفارش دومی** می‌سازد — دقیقاً همان فاکتور تکراری که `place()` برای جلوگیری
از آن نوشته شده بود، این‌بار از در تخفیف. `redemptionOnOpenOrder` این را می‌بندد: مصرفِ خودِ
مشتری روی سفارشی که هنوز پرداخت نشده، **همان سفارش است**.

پیمایش ۲۰۲۶-۰۸-۱۴ روی ربات تست: تایپ `WALK25` (با حروف بزرگ) روی پلن ۱۹۵٬۰۰۰ →
«۴۸٬۷۵۰ تومان تخفیف» → قابل پرداخت ۱۴۶٬۲۵۰ → ثبت سفارش → بازگشت و **ثبت سفارش دوباره**.
دیتابیس: **یک سفارش** (`discount_irr = 487500`, `total_irr = 1462500`) و **یک redemption**.
بعد کد هدیه: `hediye` → ۵۰٬۰۰۰ تومان به کیف پول، و بار دوم «قبلاً استفاده کرده‌اید» — دفتر
کیف پول یک ردیف `GIFT_CODE` دارد و بس.

**و یک ایراد که باز هم مرورگر گرفت:** صفحهٔ کیف پول برچسب فارسی نداشت و خام نوشت
`GIFT_CODE`. kind جدید اضافه کرده بودم و `ENTRY_LABEL` را نه.

**هنوز نه:** ورودی کد روی مسیر **تمدید**. تنها کد زندهٔ نوع `RENEW` از همان‌جا استفاده
می‌شود و امروز دکمه‌اش نیست؛ `applies_to` و اعتبارسنجی‌اش آماده است.

### ۲۰۲۶-۰۸-۱۴ (ه) — کارت مصرف: ده کاراکتر به‌جای یک PNG

فاکسیما (`infocard.php`) این را تصویر ۸۰۰×۴۰۰ با GD می‌سازد — کارت تیره، گیج دایره‌ای، فونت
فارسی همراهش، و یک فایل موقت به ازای هر بار دیدن. **ده کاراکتر همان کار را می‌کنند**: بدون
کتابخانهٔ تصویر، بدون فونت، بدون نوشتن روی دیسک، و هر کلاینت تلگرام از قبل رندرشان می‌کند
چون متن‌اند.

```
📦 حجم: 20 گیگابایت
██████░░░░ 62%
📊 مصرف شده: 12.4 گیگابایت
🎯 باقی‌مانده: 7.6 گیگابایت
```

دو تصمیم که تست‌شان دارند:

- **ایزولهٔ جهت (`U+2066` … `U+2069`) تزئین نیست.** این خط داخل پیامی است که جهت پاراگرافش راست‌به‌چپ است و
  کاراکترهای بلوک جهت خودشان را ندارند؛ بدون ایزوله، نوار جهتِ متن فارسی را می‌گیرد و از
  سمت مخالف پر می‌شود.
- **۱۰۰٪ رزرو شده است.** سهمیهٔ ۹۹.۷٪ نُه خانه و «۹۹٪» نشان می‌دهد. گفتن «تمام شد» به
  مشتری‌ای که سرویسش کار می‌کند یک تیکت پشتیبانی است.

**و یک ایراد که مرورگر گرفت و تست نگرفته بود.** اول `Math.floor` بود؛ دیتابیس ۶۲.۰۰٪ داشت و
صفحه **۶۱٪** نشان داد، چون تقسیم یک مو زیر ۶۲ می‌افتد. حالا گرد می‌شود و سقف ۹۹ سر جایش است.
تستِ `usageBar(13_314_398_617, 20)` دقیقاً همان ردیف سیم است.

پیمایش ۲۰۲۶-۰۸-۱۴ روی ربات تست: سرویس ۶۲٪ → شش خانه و «62%» · سرویس ۹۹.۸٪ → نُه خانه و
«99%» (نه ۱۰۰) و هشدار «حجم رو به پایان است» هم در همان لحظه رسید.

**آنچه ساخته نشد:** تصویر PNG. یک وابستگی native (skia/canvas) به‌علاوهٔ فایل فونت می‌خواهد
تا چیزی را بکشد که متن از قبل می‌کشد. اگر روزی طرح گرافیکی خواسته شد، همین‌جا اضافه می‌شود.

### ۲۰۲۶-۰۸-۱۴ (د) — حجم اضافه و زمان اضافه

قلم آخر از «اکشن‌های سرویس». مشتری دکمه می‌زند، **یک عدد تایپ می‌کند**، و می‌پردازد.

**قیمت‌ها را از قبل ادمین گذاشته و در `config` هر پنل نشسته‌اند** — همان ردیف میراثی که
مهاجرت کامل آورد. پنل VIP در پروداکشن: `{"f":"50000","n":"5000","n2":"5000"}` برای حجم و
`{"f":"15000","n":"4000","n2":"4000"}` برای زمان، به تومان. واحدها هم از خود PHP آمد:
`index.php:2702` مبلغ را بر نرخ تقسیم می‌کند تا **روز** دربیاورد و `:2116` نرخ را در
**گیگابایت** ضرب می‌کند. `f` مشتری عادی است و `n`/`n2` نماینده.

**یک تلهٔ واقعی که سر راه پیدا شد.** در حالت `ADD` آداپتور، `null` یعنی «بی‌نهایت». اگر خرید
حجم اضافه را با `durationDays: null` می‌فرستادیم، انقضا پاک می‌شد؛ و اگر با
`anchor + 0` می‌فرستادیم، روی حسابی که **اصلاً انقضا ندارد** تاریخ امروز مهر می‌خورد و سرویس
مشتری همان لحظه می‌مرد. حالا صفر یعنی «به این بُعد چیزی اضافه نکن» و با تست ثابت شده.

سه تصمیم دیگر:

- **افزودنی همیشه `ADD` است، هرگز `RESET`.** RESET کار تمدید است؛ روی «۵ گیگ اضافه» یعنی
  دور ریختن هر چه مشتری داشته. با برگرداندنش دو تست قرمز شد.
- **افزودنی پلن ندارد** (`plan_id IS NULL`) و ستون‌های پلنِ سرویس را دست نمی‌زند — وگرنه نام
  و مدت سرویس پاک می‌شد.
- حساب پول در **اسکیما** بسته می‌شود، نه در کد: `quantity` گیگ یا روز است، `unit_price_irr`
  نرخ یکی، و CHECK قدیمی `total = unit × quantity − discount` صحتش را می‌سنجد.

عدد تایپ‌شده ورودی بی‌اعتماد است: فقط رقم، ارقام فارسی هم پذیرفته می‌شود، سقف ۱۰۰۰، و
سرویس دوباره از `owned.ts` خوانده می‌شود.

۹ تست در `apps/bot/test/addon.test.ts` + ۵ تست قیمت در `packages/domain`.

**پیمایش با Playwright:** «➕ حجم اضافه» → تایپ «۳» → فاکتور ۱۵۰٬۰۰۰ تومان → پرداخت از کیف
پول → «✅ 3 گیگابایت به «۱ماهه - ۲۰ گیگ» اضافه شد». بعد دو طرف جدا خوانده شد — دیتابیس ما
۲۳ گیگ با همان تاریخ ۲۲ شهریور، و خودِ پنل `data_limit = 23 GiB` با همان `expire`.

### ۲۰۲۶-۰۸-۱۴ (ج) — اکشن‌های سرویس، و پنل قلابی که بالاخره ساخته شد

دو دکمه روی صفحهٔ سرویس که تا امروز فقط در ربات PHP بود: **تغییر لینک اشتراک** و
**خاموش/روشن کردن سرویس**. هر دو endpoint از خودِ PHP زنده درآمد، نه از حدس:

```
revoke   Marzban.php:197        POST /api/user/{u}/revoke_sub
on/off   panels.php:1659-1666   PUT  /api/user/{u}  {"status": "active"|"disabled"}
```

آداپتور یک متد جدید دارد — `act(action, provider)` — و آداپتوری که نداردش (مثل `manual`)
اصلاً دکمه‌اش نمایش داده نمی‌شود. **وضعیت فرستاده می‌شود، نه toggle**: اگر از روی نسخهٔ خودمان
معکوسش می‌کردیم، یک ردیف کهنه سرویس مشتری را دوباره روشن می‌کرد.

سه قاعده که تست‌ها نگه می‌دارند (`apps/bot/test/actions.test.ts`، ۹ تست):

- ردیف فقط از `owned.ts` خوانده می‌شود؛ id دیگری یعنی «سرویس پیدا نشد» و **پنل اصلاً صدا زده
  نمی‌شود**. با برداشتن `AND user_id = ?` قرمز شد.
- پنلی که خطا می‌دهد **هیچ‌چیز در دیتابیس ما عوض نمی‌کند**.
- وضعیتی که ذخیره می‌شود همانی است که **پنل می‌گوید**، نه چیزی که خواسته بودیم.

**`sim/fake-panel.mjs` — قلم معوق «پنل پاسارگاد قلابی» انجام شد.** یک سرور کوچک در حافظه
(`pnpm sim:panel`) که token، ساخت کاربر، GET، PUT، `revoke_sub` و `/api/users` را جواب
می‌دهد. **شاهد شکل پنل واقعی نیست** — چیزی را جواب می‌دهد که آداپتور ما می‌فرستد؛ ارزشش این
است که مسیر تحویل و اکشن‌ها را آفلاین قابل پیمایش می‌کند.

**پیمایش با Playwright (۲۰۲۶-۰۸-۱۴):** خرید → پرداخت از کیف پول → **تحویل روی پنل قلابی** →
«سرویس های من» → تغییر لینک (لینک از `/3` به `/4` عوض شد) → خاموش (وضعیت «غیرفعال»، لینک
پنهان، دکمه برعکس شد) → روشن. آخرش دو طرف را جدا خواندم: دیتابیس ما `ACTIVE` و
`…/sub/…/4`، خودِ پنل `active` و همان لینک.

**هنوز نیست:** حجم اضافه و زمان اضافه. آن دو مسیر پول‌اند و از همان `place()` رد می‌شوند که
تمدید رد می‌شود؛ برش بعدی.

### ۲۰۲۶-۰۸-۱۴ (ب) — انبار کانفیگ: وقتی پنل جواب نمی‌دهد، فروش نخوابد

تا امروز پنلِ در دسترس‌نبودن یعنی `retryable`، سفارش برمی‌گشت به `PAID` و تا ابد دوباره تلاش
می‌شد. پول مشتری گرفته شده و هیچ‌چیز نمی‌رسد — یعنی فروش عملاً می‌خوابد تا کسی متوجه شود.

**`migrations/0010_provisioning_stock.sql`** یک قفسه اضافه می‌کند: کانفیگ‌هایی که از قبل روی
یک پنلِ سالم ساخته شده‌اند و بی‌صاحب منتظرند. `apps/bot/src/stock.ts` وقتی سفارشی بیشتر از
**۱۰ دقیقه** در حال شکست بوده یکی را برمی‌دارد و کار را تمام می‌کند.

سه تصمیم که در خودِ اسکیما نشسته‌اند، نه در کد:

| تضمین | چه چیزی نگهش می‌دارد |
| --- | --- |
| یک کانفیگ حداکثر یک بار فروخته می‌شود | شرط `status = 'AVAILABLE'` داخل همان UPDATE + `idx_stock_one_order_per_row` |
| یک سفارش حداکثر یک کانفیگ می‌گیرد | `idx_stock_one_row_per_order` |
| یک اکانت پنل دو بار روی قفسه نمی‌رود | `idx_stock_account_once (provider_id, remote_username)` |

**چرا مهلت ۱۰ دقیقه:** قفسه دستی پر می‌شود و محدود است؛ یک قطعی سی‌ثانیه‌ای نباید خالی‌اش کند.
`updated_at` برای این کار به درد نمی‌خورد چون هر retry بازنویسی‌اش می‌کند و سفارش همیشه تازه
به نظر می‌رسد — برای همین ستون `orders.provision_first_failed_at` اضافه شد.

**تمدید از قفسه برنمی‌دارد.** تمدید باید همان اکانتی را که مشتری دارد روی همان پنل تمدید کند؛
دادن یک اکانت دیگر یعنی مشتری یک سرویس دوم می‌گیرد و اولی بی‌صدا گم می‌شود.

۷ تست جدید در `apps/bot/test/stock.test.ts`، و هر سه گارد با برگرداندنشان **قرمز دیده شدند**.
سه ادعای جدید هم به `verify_invariants.sql` اضافه شد (حالا ۲۲ PASS).

**هنوز نیست:** رابطی برای پر کردن قفسه. امروز با `INSERT` انجام می‌شود؛ صفحه‌اش با پنل ادمین
می‌آید. هیچ هشداری هم برای «قفسه خالی شد» وجود ندارد.

### ۲۰۲۶-۰۸-۱۴ — کیف پول روی مرورگر راه رفت، و دو ایراد در راه پیدا شد

مسیر کامل روی ربات تست با Playwright پیموده شد — نه استدلال از روی کد:
`/start` → «کیف پول + شارژ» (موجودی صفر) → «افزایش موجودی» → ۳۰۰٬۰۰۰ تومان → صفحهٔ کارت →
«پرداخت کردم» → **پیامک بانکی واقعی روی `POST /api/v1/sms`** → تایید خودکار → شارژ کیف پول
(«✅ کیف پول شما شارژ شد») → خرید یک پلن ۱۰۰٬۰۰۰ تومانی → «💰 پرداخت از کیف پول» →
«موجودی باقی‌مانده: ۲۰۰٬۰۰۰ تومان» و سفارش `COMPLETED`.

سمت دیتابیس هم همان را می‌گوید: `wallet_entries` دو ردیف دارد — `TOPUP +3,000,000` با کلید
`order:3:topup` و `PURCHASE −1,000,000` با کلید `order:4:purchase` — و `wallets.balance_irr`
که تریگر می‌سازد برابر ۲٬۰۰۰٬۰۰۰ است. تصویرها در `.playwright-mcp/w-0*.png` (کامیت نمی‌شوند).

**ایراد ۱ — هیچ دستگاه seed‌شده‌ای نمی‌توانست به ingest احراز هویت کند.**
`generators.ts` پیشوند توکن را دستی می‌نوشت: `tok-` + سه حرف اول کد دستگاه = **هفت** کاراکتر.
ingest اما با `apiKey.slice(0, 4)` و تساوی دقیق می‌گردد. یعنی هیچ‌وقت پیدا نمی‌شد. کسی ندید
چون هر تست ingest اعتبارنامهٔ خودش را می‌سازد — دقیقاً قاعدهٔ ۶: تست فقط با خودش می‌خواند.
حالا پیشوند از `tokenPrefix()` مشترک می‌آید و کلید هم شکل واقعی دارد (۶۴ هگز).

**ایراد ۲ — و ایراد ۱ آن را لو داد.** وقتی کلیدها را به `token-phone-a-…` تغییر دادم، هر شش
دستگاه پیشوند `toke` گرفتند و **فقط یکی‌شان توانست پیامک بفرستد**: کوئری
`WHERE token_prefix = ?1 ... LIMIT 1` هر ردیفی را که planner برمی‌داشت می‌داد و به بقیه
`invalid_key` می‌گفت. پیشوند فقط ۴ کاراکتر از توکن است، پس این در پروداکشن هم ممکن است — با
۱۰۰ اعتبارنامه حدود ۸٪. کوئری حالا `AND device_id = ?2` دارد. تست جدید در
`security.test.ts` دو دستگاه با پیشوند یکسان می‌سازد؛ **با برگرداندن کوئری قرمز شد**.

**نکته‌ای که ایراد نیست:** اولین تلاش تسویه نشد و claim روی `AMBIGUOUS_TRANSACTIONS` ماند.
علتش خودم بودم — دو واریز هم‌مبلغ به یک کارت داخل پنجرهٔ ۵ دقیقه فرستاده بودم. موتور تطبیق
دقیقاً همان کاری را کرد که باید: جفت غیرایزوله auto-verify نمی‌شود. دستور تکرارپذیرِ تزریق
پیامک حالا در `sim/README.md` است، با همین تله.

### ۲۰۲۶-۰۸-۱۳ (د) — پنل ما مرزبان نیست، پاسارگاد است

Sam این را گفت و درست می‌گفت. شاهدش از قبل داخل هدر خودِ `marzban.ts` نوشته شده بود — جدول
پنج پنل زنده با ستون `version = 1` — و من ستون را ثبت کرده بودم بی‌آنکه معنایش را بخوانم.

معنایش در `legacy/mirzabot-php/admin.php:749-750` است:

```php
$version_panel = $userdata['type'] == "pasarguard" ? "1" : "0";
$userdata['type'] = $userdata['type'] == "pasarguard" ? "marzban" : $userdata['type'];
```

میرزا نوع `pasarguard` ندارد، پس انتخاب ادمین را زیر نام مرزبان بایگانی می‌کند و حقیقت را
در ستون دوم می‌گذارد. هر ۵ پنل پروداکشن `version_panel='1'` دارند و آدرسشان هم
literally `pasargad.…` است. مهاجرت ما فقط `type` را برمی‌داشت، پس `kind='marzban'` روی هر
پنج ردیف **نام مستعار میراثی بود، نه واقعیت**.

آداپتور تصادفاً درست بود — شاخهٔ `version_panel==1` در `Marzban.php:229` همان
`group_ids` + `proxy_settings` را می‌فرستد که ما می‌فرستیم. سه چیز دیگر درست نبود:

| نقص | چه بود | چرا هیچ تستی نمی‌دیدش |
| --- | --- | --- |
| `config.inbounds` و `config.proxies` **رشته** بودند | `"[42,2]"` به‌جای `[42,2]`. MySQL متن می‌دهد و `legacyAttrs` عیناً ذخیره می‌کرد. آداپتور رشته را به‌عنوان `group_ids` می‌فرستاد → **۴۲۲ روی اولین تحویل واقعی** | هر سه fixture موجود مقدار **پارس‌شده** می‌دادند. با کد موافق بودند، با پروداکشن نه |
| `config` یک **JWT زندهٔ ادمین پنل** داشت | ستون `datelogin` وارد `config` می‌شد، درست زیر کامنتی که می‌گفت این ردیف «امن است که به پشتیبان داده شود» | هیچ تستی محتوای `config` را برای اسرار نمی‌گشت |
| `kind` دروغ می‌گفت | و `version_panel` فقط به‌صورت رشته‌ای در `config` می‌ماند که هیچ کدی نمی‌خواندش | — |

**اول تست، بعد اصلاح.** `packages/migrate/test/providers.mysql.test.ts` ردیف‌های واقعی
`marzban_panel` را از MySQL شبیه‌سازی می‌خواند و از **همان توابع** مهاجرت رد می‌کند
(`providerRow` عمداً export شده تا تست کپی دوم نسازد). **چهار تست قرمز شدند**، بعد اصلاح،
بعد سبز. ادعاها باریک‌اند و هیچ مقداری چاپ نمی‌کنند — این ردیف‌ها اعتبارنامهٔ پنل دارند.

**چه چیزی عوض شد**

- `transform.ts` — `parseJsonStrings` (متن JSON‌شکل → JSON؛ چیزی که پارس نشود **دست‌نخورده**
  می‌ماند، نه اینکه به `{}` تبدیل شود) و دو نگاشت `PANEL_TYPE` / `PANEL_VERSION`
- `migrate.ts` — `providerKind` (صادر شده)، `PROVIDER_SECRETS` = `password_panel` +
  `datelogin` + `secret_code`
- `migrations/0009_pasarguard_kind.sql` — `pasarguard` به CHECK اضافه شد
- `marzban.ts` — `kind: 'pasarguard'`، و هدر حالا می‌گوید version 1 یعنی چه
- `preflight.ts` — دو چک جدید روی `marzban_panel`؛ `verify.ts` — چک JSON-as-text و توکن
- `catalog.ts` — سید از `DO NOTHING` به `DO UPDATE` رفت (پایین)

**`marzban` عمداً روی فهرست «بدون آداپتور» ماند.** یک پنل مرزبان کلاسیک واقعی است، ولی
فیلدهایش `inbounds`/`proxies` است. اگر به این آداپتور می‌رسید، `group_ids` می‌گرفت، بی‌صدا
دورش می‌انداخت، و مشتری اکانتی بدون inbound تحویل می‌گرفت. سقوط به `manual` خرابیِ بلند است.

**سیدی که همگرا نبود.** `seedCatalog` ادعا می‌کرد «دیتابیس روی آنچه این‌جا نوشته شده همگرا
می‌شود» ولی `ON CONFLICT DO NOTHING` فقط قول می‌دهد اجرای دوباره چیزی **اضافه** نکند. وقتی
`sim-vip` از `marzban` به `pasarguard` رفت، هر دیتابیس از قبل سیدشده مقدار قدیمی را نگه
داشت — و `marzban` دیگر آداپتور ندارد، پس آن پنل بی‌صدا دستی می‌شد. حالا `DO UPDATE` است.

**آنچه هنوز باز است.** `panel:schema` روی پنل واقعی اجرا شد (یک GET، با اجازهٔ صریح Sam):
**HTTP 404** — پنل `openapi.json` نمی‌دهد، یعنی `DOCS` خاموش است. این درست‌ترین حالت
امنیتی برای پروداکشن است ولی یعنی نسخهٔ پنل را نمی‌دانیم. پس مسیرهای `/api/user/{username}`
**دست نخوردند**: پاسارگاد آن‌ها را deprecate کرده به نفع `by-id`، ولی `Marzban.php` هر روز
همان‌ها را روی همین پنل‌ها می‌زند و کار می‌کند. تعویض کور یعنی ۴۰۴ روی lookup، بعد ۴۰۹ روی
create، بعد `retryable` — سفارشی که برای همیشه در `PAID` می‌چرخد.

از سورس `PasarGuard/panel` این را می‌دانیم: `note` در `UserModify` هست (از `User` ارث
می‌رسد) و `expire` هم `int` و هم ISO می‌پذیرد. پس بدهی «یک تمدید روی پنل واقعی لازم است
تا ببینیم `note` می‌ماند» از **مسدودکنندهٔ سوئیچ** خارج شد.

### ۲۰۲۶-۰۸-۱۳ (ج) — سرویس‌های من، تمدید، و هشدار انقضا

سه چیزی که بین «سیستم جدید کار می‌کند» و «خریدهای جدید را به سیستم جدید بسپاریم» ایستاده
بودند. با این سه، آن فاصله بسته است.

#### لینک اشتراک هیچ‌جا ذخیره نمی‌شد

میرزابات هر بار که کسی سرویسش را باز می‌کند از پنل می‌پرسد (`admin.php:6212`). این‌جا آن
صفحه **داخل تراکنشی** کشیده می‌شود که `update_id` را claim کرده، پس یک پنل کند قفلِ
«دقیقاً یک بار» را ۲۰ ثانیه باز نگه می‌داشت.

پس مهاجرت `0008` دو ستون اضافه کرد — `subscription_url` و `used_bytes` — و
`last_synced_at` که از اول وجود داشت و هرگز نوشته نمی‌شد بالاخره معنا پیدا کرد. تحویل، لینک
را می‌نویسد؛ یک sweep هر ۱۰ دقیقه **یک لیست به ازای هر پنل** می‌گیرد و مصرف را تازه می‌کند.
به ازای ۳٬۱۳۹ سرویس این یعنی ۵ درخواست در ۱۰ دقیقه، نه یک درخواست به ازای هر نگاه.

**عمداً sync نمی‌شود:** `status` و `expires_at`. واژگان مرزبان
(active/limited/expired/disabled/on_hold) روی شش مقدار مجاز این ستون نگاشت صادقانه ندارد، و
تاریخ را ما فروخته‌ایم پس ما مالکش هستیم — ساعتِ غلطِ یک پنل نباید بتواند چیزی را که مشتری
خریده کوتاه کند. «منقضی» و «حجم تمام‌شده» موقع نمایش از دو ستونی که قابل گم‌شدن نیستند
استنتاج می‌شوند.

**سرویس مرده لینکش را نمی‌دهد.** لینک بعد از تمام‌شدن حجم هم باز می‌شود و کار نمی‌کند؛ دادنش
بدون هشدار همان چیزی است که «وارد کردم کار نکرد» را می‌سازد.

#### تمدید — و چرا «همان پلن قبلی» جواب نمی‌داد

اولین طراحی این بود که همان پلنِ خریداری‌شده تمدید شود. دیتای واقعی ردش کرد: از ۳٬۱۳۹ سرویس
فعال فقط **۱٬۶۸۷** تا نامشان با محصولی که هنوز وجود دارد می‌خورد، و `subscriptions.plan_id`
برای **هر** ردیف مهاجرت‌شده NULL است. یعنی «همان پلن» به نیمی از مشتری‌ها می‌گفت سرویس‌تان
قابل تمدید نیست. پس مشتری از پلن‌های فعلیِ **همان پنل** انتخاب می‌کند.

**دو حالت تمدید، چون پروداکشن دو تا دارد** (`marzban_panel.Methodextend`):

| پنل        | تنظیم                             | رفتار                                      |
| ---------- | --------------------------------- | ------------------------------------------ |
| ۱ (VIP)    | «اضافه شدن زمان و حجم به ماه بعد» | `ADD` — باقی‌ماندهٔ فعلی حفظ می‌شود        |
| ۸/۱۲/۱۳/۱۴ | «ریست حجم و زمان»                 | `RESET` — ساعت از نو، شمارندهٔ مصرف صفر    |
| ۱۳         | `status_extend = off_extend`      | تمدید روی این پنل خاموش است — رعایت می‌شود |

سه حالت دیگرِ `panels.php:extend` پیاده نشدند، به همان دلیلی که شاخه‌های `on_hold` نوشته
نشدند: هیچ ردیفی انتخابشان نمی‌کند.

**تمدید اولین عملیاتی است که ذاتاً تکرارپذیر نیست.** سی روز دو بار یعنی شصت روز، و مشتری
هیچ‌وقت گزارشش نمی‌کند. وضعیت سفارش یک‌بار بودن را نگه می‌دارد، و آداپتور یک نگهبان دوم دارد:
`public_id` سفارش را در `note` حساب می‌نویسد و قبل از هر تغییر می‌خواندش. تستش دقیقاً همان
سناریو است — timeout، برگشت به `PAID`، تلاش دوباره.

#### هشدار انقضا و حجم

آستانه‌ها از خودِ `setting` آمده‌اند نه از حدس: `volumewarn = 1` گیگ و `daywarn = 2` روز.
`cron_status` می‌گوید `remove` و `remove_volume` هر دو `false`‌اند — یعنی حذف خودکار سرویسِ
منقضی در پروداکشن **خاموش** است، پس ساخته نشد.

هر هشدار یک بار، با همان ستون و همان دو کلیدی که PHP استفاده می‌کند (`subscriptions.notify`)،
و تمدید پاکش می‌کند تا دورهٔ بعد دوباره هشدار برود.

#### شکل `expire` — از خودِ PHP درآمد، نه از پنل واقعی

اول نوشته بودم «این را فقط روی پنل واقعی می‌شود فهمید». غلط بود. PHPِ زنده هر روز روی همین
پنج پنل کار می‌کند و خودش جواب را دارد — و **دو جواب متفاوت** می‌دهد که به عملیات بستگی
دارد، نه به پنل:

| عملیات                     | جای کد            | چه می‌فرستد                 |
| -------------------------- | ----------------- | --------------------------- |
| ساخت (`version_panel = 1`) | `Marzban.php:242` | `date('c', $ts)` → ISO-8601 |
| تمدید (`type = marzban`)   | `panels.php:1958` | `$time_new` → ثانیهٔ یونیکس |

ساخت ما از اول ISO می‌فرستاد و درست بود. **تمدید ما هم ISO می‌فرستاد و غلط بود** — عوض شد به
عدد. سه تست با ارجاع به همان دو خط PHP این را قفل می‌کنند، تا کسی بعداً «ناهماهنگی» را
یکدست نکند.

خواندن هر دو شکل را قبول می‌کند و لازم هم هست: حسابی که ما ساخته‌ایم ISO دارد و حسابی که
تمدید کرده‌ایم عدد، و تمدیدِ حالت ADD باید از هرکدام درست حساب کند.

**آنچه هنوز روی پنل واقعی می‌ماند:** فقط اینکه `note` روی `PUT` پذیرفته شود — نگهبانِ دومِ
یک‌بار-اجرا به آن تکیه دارد و PHP این فیلد را در تمدید نمی‌فرستد. یک تمدید روی ربات تست
کافی است.

### ۲۰۲۶-۰۸-۱۳ (ب) — تحویل سرویس؛ زنجیره تا آخر بسته شد

تا امروز سفارش روی `PAID` می‌ماند و **هیچ سرویسی تحویل نمی‌شد**. این تنها چیزی بود که
سپردن خریدهای جدید به سیستم جدید را غیرممکن می‌کرد.

**تصمیم مهم که از دیتا آمد نه از پلن:** پلن هشت نوع آداپتور فرض کرده بود. خواندن
`marzban_panel` واقعی نشان داد هر ۵ پنل **در هر بُعدی که مهم است یکسان‌اند** —
`version_panel = 1` و `conecton = offconecton` و `sublink = onsublink` برای هر پنج‌تا. پس
`marzban.ts` **یک مسیر** دارد، نه چهار شاخهٔ `adduser` در PHP. آن شاخه‌ها کد حذف‌شده نیستند؛
کدی‌اند که اصلاً نوشته نشد، و جدول پنل‌ها دلیلش است.

```
PAID ──claim──▶ PROVISIONING ──▶ COMPLETED
                     │
                     └──▶ FAILED (failure_reason را آدم می‌خواند)
```

**idempotency از نام کاربری می‌آید، نه از یک قفل.** نام حساب از `public_id` سفارش ساخته
می‌شود (`{telegramId}_{publicId}` — همان شکلی که الان در پنل‌ها هست). پس sweepای که حساب را
ساخت و قبل از نوشتن ردیف مُرد، دفعهٔ بعد همان نام را می‌خواهد و همان حساب را پیدا می‌کند.

**دو باگ واقعی که فقط تست پیدایشان کرد — هر دو در کد من، نه در تست:**

1. اول ۸ کاراکتر اول `public_id` را می‌گرفتم چون نام‌های واقعی پروداکشن ۸ رقمی‌اند. یعنی دو
   سفارشِ **یک مشتری** می‌توانستند برخورد کنند — و حالت شکستش خطا نیست: آداپتور حساب موجود
   را پیدا می‌کند و موفقیت گزارش می‌دهد، پس مشتری دوباره پول می‌دهد و همان سرویس قبلی را
   می‌گیرد. یکتایی یک ستون آن‌طرف‌تر تضمین شده بود و من دورش انداخته بودم.
2. بررسی وجودِ حساب روی هر وضعیتِ غیر ۴۰۴ `throw` می‌کرد و `catch` بیرونی همه را
   «دوباره تلاش کن» می‌کرد. یعنی پنلی که دسترسی ادمینش قطع شده (۴۰۳) **تا ابد** retry
   می‌شد به‌جای رسیدن به یک آدم.

**اعتبارنامهٔ پنل هرگز از دیتابیس نمی‌آید.** `secret_ref` فقط یک _نام_ است و مقدارش از
`PANEL_<REF>` در محیط خوانده می‌شود — همان چیزی که کامنت اسکیمای `provisioning_providers`
وعده داده بود. جدول امن می‌ماند برای dump و لاگ و دادن به پشتیبانی.

**محصولی که آداپتور ندارد `manual` می‌شود** — پنج نوع دیگرِ مجاز در اسکیما هنوز آداپتور
ندارند و همه به این می‌افتند. عمداً «موفق» گزارش می‌شود نه FAILED: پول واقعی است و فروش
انجام شده؛ چیزی که مانده یک _کار_ است نه یک _خطا_. و چون لینکی وجود ندارد، به مشتری هم
لینکی وعده داده نمی‌شود.

### ۲۰۲۶-۰۸-۱۳ — سه درخواست ادمین کل

#### ۱. ضریب نمایش کارت — و باگی که در راهش پیدا شد

ادمین خواست کارت تازه‌اضافه‌شده **بیشتر** از بقیه نمایش داده شود تا تعداد تراکنشش برسد،
ولی **نه فقط آن کارت**.

بررسی نشان داد نیمهٔ دومِ خواسته همین حالا نقض می‌شود. `rotateCard` روی
`ORDER BY last_assigned_at NULLS FIRST` بود و کارت تازه `NULL` دارد، پس **۱۰۰٪** چک‌اوت‌ها را
می‌گرفت تا وقتی از همه تازه‌تر شود. «فقط کارت جدید» وضع موجود بود، نه خطری در آینده.

جایش **round-robin وزن‌دار روی یک ساعت مجازی** نشست (`migrations/0007`):
هر کارت `rotation_cursor` دارد؛ کوچک‌ترین انتخاب می‌شود و به اندازهٔ `1000000 / display_weight`
جلو می‌رود. وزن ۳ یعنی دقیقاً ۳ برابر بیشتر. و هیچ‌وقت انحصاری نمی‌شود، چون مکان‌نمای کارتِ
انتخاب‌شده **اکیداً** زیاد می‌شود و بعد از تعداد متناهی نوبت از بقیه جلو می‌زند.

کلید ماجرا در خود ستون وزن نیست، در **مقدار اولیهٔ کارت جدید** است: روت افزودن کارت آن را
روی `MAX(rotation_cursor)` می‌گذارد. اگر صفر بگذارد، همان باگ برمی‌گردد.

`apps/bot/test/rotation.test.ts` هر دو نیمه را می‌سنجد: ۵ کارت با وزن ۳ روی یکی و ۷۰۰ انتخاب،
نتیجهٔ دقیق ۳۰۰/۱۰۰/۱۰۰/۱۰۰/۱۰۰؛ و در بیشترین وزنِ مجاز هم **هیچ کارتی صفر نمی‌گیرد**.

#### ۲. بانک‌ها — تشخیص از روی کارت و پیامک، قابل ویرایش در داشبورد

تب جدید **Banks**. دو چیز که تا امروز فقط با دیپلوی عوض می‌شدند:

- **پیشوند کارت → بانک** (`bank_card_prefixes`، ۴۴ ردیف). بلندترین پیشوند برنده است، پس
  تقسیم‌شدن یک رِنج در آینده یعنی یک ردیف بیشتر و صفر خط کد.
  **صحت‌سنجی بیرونی:** هر ۱۱ پیشوند متمایزی که در دیتای واقعی پروداکشن استفاده شده resolve
  می‌شود، صفر ناشناخته. و `505416 → GARDESHGARI` با کارت‌های سالم همان بانک جور است.
- **پترن پیامک بانک** (`bank_sms_patterns`). این‌جا **قاعدهٔ ایمنی مهم‌تر از خود فیچر است:**
  یک ردیف دیتابیسی **هرگز** پارسر داخلی را override نمی‌کند. فقط جایی اجرا می‌شود که زنجیرهٔ
  ۱۴-پارسری هیچ بانکی نام نبرده باشد، و اگر پارسر داخلی پول را از قبل خوانده باشد فقط **نام
  بانک** را اضافه می‌کند و به مبلغ دست نمی‌زند. OTP را اصلاً نمی‌بیند.

**درسی که فقط با اجرا به دست آمد:** شرط اولیه‌ام «اگر پارسر داخلی `matched` بود دست نزن» بود.
اجرای واقعی نشان داد `generic-balance` برای یک پیامک واریز `matched: true` برمی‌گرداند با
`classification: 'BALANCE'` و `amountIrr: null` — یعنی هیچ پولی نخوانده. آن شرط، پترن‌ها را
دقیقاً از پیامک‌هایی که برای نجاتشان ساخته شده‌اند بیرون نگه می‌داشت. شرط درست
«`BANK_TRANSACTION` با مبلغ غیر-null» است. **یک کامنت که می‌گوید چرا چیزی امن است، شاهد نیست.**

مرز اعتماد: قبل از `enabled` شدن، هر فیلد الگو جدا روی ورودی طعمه با بودجهٔ زمانی اجرا می‌شود.
دو بار خودِ همین گیت اشتباه بود و در `apps/dashboard-worker/src/bankRoutes.ts` مستند شده — یک بار

`luhnOk` هم اضافه شد — روی ۲۵ کارت واقعی ربات صفر ناسالم، و `5054161716277062` (مورد ۴ فایل

#### ۳. جدایی ربات و داشبورد

### داشبورد روی استک جدید

**تایید شد ۲۰۲۶-۰۸-۱۲:** یک پروسهٔ Node روی `127.0.0.1:8788` هم SPA را سرو می‌کند هم API را،
روی Postgres. در کل ریپو بیرون از `legacy/` صفر فایل `wrangler.*` و صفر وابستگی `@cloudflare/*`
هست. فقط لازم بود SPA بیلد شود.

```bash
corepack pnpm --filter @shikoo/admin-web build   # یک بار، dist ساخته می‌شود
DATABASE_URL=... TEST_ACCESS_USER=you@example.com corepack pnpm --filter @shikoo/dashboard start
```

**تصمیم Sam، ۲۰۲۶-۰۸-۱۲ — و بازنگری‌اش ۲۰۲۶-۰۸-۱۶.** آن روز قرار بود فقط Workers و D1 حذف
شوند و Access بماند، چون یعنی لاگین را خودمان ننوشته‌ایم. چهار روز بعد Access حذف شد: نه به
خاطر امنیت، بلکه چون **دو `aud` جدایش تنها مانع ساختاری ادغام پنل‌ها بود** و ادمین کل ادغام را
خواسته بود. جایش `operatorSession.ts` است — رمز با scrypt، TOTP طبق RFC 6238، کوکی
`HttpOnly`، و قفل پنج‌تلاشی که Postgres در همان `UPDATE` نگه می‌دارد. Tunnel هنوز سر جایش است.

**دو رشتهٔ ثابت که موقع دیپلوی باید عوض شوند** (الان به دیپلوی قدیمی اشاره می‌کنند، پس
ناخواسته درست کار می‌کنند تا وقتی مهاجرت نکرده‌ایم):

| کجا                                     | چه چیزی                                                     |
| --------------------------------------- | ----------------------------------------------------------- |
| `apps/dashboard-worker/src/security.ts` | origin مجاز `dashboard-worker.samsos.workers.dev`           |
| `apps/dashboard-worker/src/index.ts`    | `DEFAULT_INGEST_URL` روی `ingest-worker.samsos.workers.dev` |

**این مانع برداشته شد (۲۰۲۶-۰۸-۱۲).** دو چیز جلوی رندر شدن این صفحه را گرفته بود، و مهم‌ترش
آنی نبود که اول دیده شد:

1. `packages/seed/src/run.ts` یک **استاب خالی** بود. سید فقط داخل هارنس vitest روی D1 اجرا
   می‌شد، پس هیچ‌وقت هیچ راهی برای پر کردن Postgres شبیه‌سازی وجود نداشت. حالا
   `pnpm --filter @shikoo/seed seed:sim` هست — پاک می‌کند، سید می‌زند، و اگر میزبان
   `localhost` نباشد **اجرا نمی‌شود**.
2. سید `source_system = 'manual'` می‌نوشت و همهٔ تب‌ها `'MIRZABOT'` می‌خواهند. حالا
   `MIRZABOT_SOURCE` می‌نویسد.

سید همچنین **۳۶ ردیف `payment_cards`** می‌سازد (قبلاً صفر). بدون آن هیچ claim نمی‌تواند کارت
را به حساب برساند و همه `UNMAPPED_CARD` می‌شوند — یعنی مسیر تایید خودکار اصلاً قابل تست نبود.
شماره‌ها Luhn-معتبرند: کارتی که نمی‌تواند وجود داشته باشد، یک بررسی واقعی را پنهان می‌کند.

### زنجیرهٔ پرداخت — سفارش تا تایید خودکار

`سفارش → کارت مقصد → «پرداخت کردم» → claim → پیامک بانک → AUTO_VERIFIED`

`source_system` نام **پروتکل کارت‌به‌کارت** است، نه نام بات. موتور تصمیم
(`mirzabotMatch.ts:89`)، همهٔ کوئری‌های داشبورد، و مهم‌تر از همه استثنای
`matching.ts:101` که اسکورر عمومی را از این claimها دور نگه می‌دارد، همه روی همین یک مقدار
سوارند. مقدار تازه برای ربات جدید یعنی claimهای ما **داخل** اسکورر عمومی می‌افتند — همان
باگی که اسکیل `mirzabot-matching` صریحاً هشدارش را می‌دهد. مبدأ از پیشوند
`external_order_id` خوانده می‌شود: `shikoo:` برای ربات جدید، `mirzabot:` برای PHP.
تصمیم Sam، ۲۰۲۶-۰۸-۱۲.

انتخاب کارت چرخشی LRU است روی `idx_payment_cards_rotation` با `FOR UPDATE SKIP LOCKED` —
بدون جدول لیز. لیزها در ریپوی PHP می‌مانند.

تایید سرتاسری روی محیط شبیه‌سازی، ۲۰۲۶-۰۸-۱۲: سفارش `d2154af80e` → claim
`shikoo:84702b7df0` به مبلغ ۱٬۰۰۰٬۰۰۰ ریال روی «Saderat Test Phone 5» → پیامک اعتبار ۲۰
ثانیه بعد → `AUTO_VERIFIED` با `timeDeltaSeconds = 20`، روی تب `bot_auto_verified` داشبورد.

### تسویه — از claim تاییدشده تا سفارش پرداخت‌شده

`apps/bot/src/settle.ts`. هاب claim را VERIFIED می‌کند (خودکار از روی SMS، یا با تایید دستی
ادمین) و هیچ‌کدام از آن دو مسیر چیزی از `orders` نمی‌داند — و نباید بداند. جوش بین دو دنیا
`external_order_id` است که `public_id` پرداخت ما را حمل می‌کند.

جاروب است نه callback، چون رویدادِ تصمیم در پروسهٔ دیگری می‌افتد؛ و جاروب ری‌استارت وسط کار را
هم تاب می‌آورد چون کارِ باقی‌مانده از روی ردیف‌ها استنتاج می‌شود نه از حافظه. از حلقهٔ poll هر
چرخه صدا زده می‌شود — بدون سرویس یا cron جدید، و با poll‌ ۲۵ ثانیه‌ای فاصلهٔ «تایید شد» تا
«مشتری خبردار شد» حداکثر یک چرخه است.

هر `UPDATE` وضعیتی را که انتظار دارد در `WHERE` خودش دارد، پس جاروب دوم هیچ ردیفی را نمی‌گیرد
و پیام دوباره فرستاده نمی‌شود.

**سفارشی که دیگر باز نیست:** پرداخت `PAID` می‌شود چون پول واقعاً رسیده، ولی سفارش لغو/منقضی
دست‌نخورده می‌ماند و یک خط `needs a human` لاگ می‌شود. این عودت وجهی است که کسی باید انجام دهد؛
`PAID` کردنِ زورکیِ سفارش، آن را پنهان می‌کرد.

**هنوز بسته نشده:** تحویل. سفارش روی `PAID` می‌نشیند و آداپتور provisioning اجرا نمی‌شود —
برش بعدی. آپلود رسید هم نیست: `receipt_submitted_at` خالی می‌ماند و پنجرهٔ انتظار روی
`paid_clicked_at` لنگر می‌اندازد، که درست کار می‌کند.

### باگی که فقط با مرورگر دیده شد

ستون «Live Statistics» صفحهٔ پرداخت‌ها اعداد پول را وسط عدد می‌شکست —
`۲,۸۱ / ۳,۶۴ / ۷ / Tom / an` به‌جای `۲,۸۱۳,۶۴۷ Toman`. علت یک قانون سراسری بود:

```css
dl {
  display: grid;
  grid-template-columns: max-content 1fr;
}
```

`.stats-rail__grid` فقط `margin` را override می‌کرد، پس گرید می‌ماند و ردیف‌هایش — که خودشان
flex‌اند — دوتا-دوتا در دو ستون می‌افتادند؛ ستون دوم به ۶۴ پیکسل و `dd` به ۲۵ پیکسل جمع می‌شد و
`word-break: break-word` بقیه‌اش را انجام می‌داد. یک خط `display: block` رفعش کرد.

روی هر دو عرض ۱۴۴۰ و ۱۹۲۰ بازتولید شد، پس ربطی به ریسپانسیو نداشت. **از روی کد پیدا نمی‌شد**:
در سورس هیچ‌جا `display: grid` برای این کلاس نیست — قانون از سلکتور `dl` می‌آمد و فقط
`getComputedStyle` در مرورگر آن را نشان داد.

### ریسپانسیو — سه علت مستقل

در عرض ۳۷۵ پیکسل کل صفحه ۹۹۷ پیکسل پهنا داشت و ۶۲۲ پیکسل افقی اسکرول می‌شد.

**۱. جدول، از راهی که `overflow` جلویش را نمی‌گیرد.** `.txn-table-wrap` از قبل
`overflow-x: auto` داشت و درست هم اسکرول می‌کرد (عرض ۳۲۶، محتوا ۱۰۰۶) — ولی عرض max-content
جدول از راه **محاسبهٔ اندازه** به والدها نشت می‌کرد، نه از راه رنگ‌شدن. برای همین
`overflow: hidden` و `overflow: clip` هیچ‌کدام اثر نداشتند و `contain: layout` داشت. عمداً
`contain: paint` نه — آن دیالوگ ردیف را هم می‌برید (با باز کردن منوی ⋮ بررسی شد).

**۲. نوار تب‌ها.** `min-width: max-content` دارد تا برچسب‌ها نشکنند؛ ۸۷۲ پیکسل تب داخل ستون
۳۲۶ پیکسلی، بدون هیچ کانتینر اسکرولی. حالا `.ops-nav` خودش اسکرول می‌کند.

**۳. هدر.** ۵۷۸ پیکسل محتوا در ۳۶۶ پیکسل جا: برند به عرض صفر جمع می‌شد ولی همچنان ۲۱۷ پیکسل
را رنگ می‌کرد و روی بج محیط و انتخاب تاریخ می‌افتاد. زیر ۶۴۰ پیکسل، wordmark حذف می‌شود
(لوگو همچنان لینک خانه است) و کنترل‌ها wrap می‌شوند.

**نکتهٔ روش:** آشکارساز اولم دو بار جواب غلط داد — یک بار محتوای داخل کانتینر اسکرول را
مثبت کاذب شمرد، یک بار `realLeaks: []` داد در حالی که صفحه واقعاً اسکرول می‌شد. چیزی که
جواب داد **دوبخشی کردن DOM** بود: هر زیردرخت را `display:none` کن و ببین `scrollWidth` کِی
می‌افتد. وقتی اندازه‌گیری با رفتار نمی‌خواند، به رفتار اعتماد کن.

تایید شده روی ۳۶۰ · ۳۷۵ · ۳۹۰ · ۷۶۸ · ۱۰۲۴ · ۱۴۴۰ · ۱۹۲۰ — در همه `sidewaysScroll = 0`.

### ⚠️ بدهی باز: UI/UX داشبورد باید بازطراحی شود

**تصمیم Sam، ۲۰۲۶-۰۸-۱۳.** کاری که تا این‌جا روی داشبورد شده **رفع خرابی بوده، نه طراحی**:
عدد پولی که وسط عدد می‌شکست، صفحه‌ای که روی گوشی افقی اسکرول می‌شد، هدری که روی خودش
می‌افتاد، لوگوی شکسته. هیچ‌کدام «طراحی خوب» نیست — فقط دیگر خراب نیست.

خودِ UI/UX هنوز آن چیزی نیست که باید باشد و **حتماً باید رویش کار شود**. ولی الان اولویت
پایین‌تری دارد از اجرایی شدن پلن؛ اول سیستم باید کار کند و بالا برود، بازطراحی بعد از آن.

وقتی نوبتش شد، این‌ها را از همین دور کار می‌دانیم و نقطهٔ شروع خوبی هستند:

- جدول ۱۱ ستونهٔ `bot_auto_verified` روی گوشی افقی اسکرول می‌شود. کار می‌کند، ولی الگوی خودِ
  این کدبیس در `TodayView` و `AccountsView` کارت است نه اسکرول افقی
  (`useMediaQuery('(max-width: 639px)')`). این صفحه هنوز به آن الگو نرسیده.
- در دیالوگ بررسی پرداخت، برای یک claim تاییدشده هم‌زمان «Waiting for bank transfer» و
  «Bot auto verified» نوشته می‌شود. متناقض است و از قبل هم بوده.
- قانون سراسری `dl { display: grid }` هر لیست تعریفی در کل داشبورد را گرید می‌کند. یک بار
  گاز گرفت؛ هر `<dl>` دیگری همان تله را دارد.
- هدر روی گوشی دو خطی می‌شود (۱۰۸ پیکسل ارتفاع). قابل قبول است، زیبا نیست.

`GET /shikoonet-logo.png` به‌جای تصویر، ۸۵۳ بایت HTML برمی‌گرداند. `server.ts` فقط
`/assets/*` را استاتیک سرو می‌کرد، ولی Vite هرچه در `public/` است را به **ریشهٔ** `dist`
کپی می‌کند — لوگو، favicon، robots.txt. همه به fallback ی SPA می‌افتادند. حالا ریشه هم سرو
می‌شود و miss به `next()` می‌رود، پس مسیرهای ناشناختهٔ SPA و `/api/` دست‌نخورده‌اند.

**آنچه از داشبورد زندهٔ shikoonet برداشته شد (فقط خواندن، هیچ دکمهٔ عملی زده نشد):**
Review ۵۲۷ (Income · Needs Review · Waiting · Suspected Fake · Bot Auto Verified) ·
Reseller (خالی) · Payments ۲۳۹ (Manually Verified ۳۷ · Declined ۲۰۲ · All ۵۸۹). صفحهٔ
Bot Auto Verified نرخ اتوماسیون ۹۵.۷٪، میانگین ۴۱ ثانیه از claim تا تراکنش بانکی، و ورودی
بانکی در برابر مانده‌های شناخته‌شده را نشان می‌دهد. **به داشبورد زنده دست زده نشد.**

**مقصد نهایی این صفحه:** وصل شدن به پرداخت و تایید از روی SMS برای سفارش‌های ربات جدید.
