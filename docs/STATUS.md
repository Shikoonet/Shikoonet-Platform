## راه‌اندازی و اجرا

```bash
pnpm install
pnpm sim:up                                   # Postgres روی 5433، MySQL روی 3307

for f in migrations/000*.sql; do              # اسکیما را بساز
  docker exec -i shikoo-sim-postgres-1 psql -U shikoo -d shikoo -v ON_ERROR_STOP=1 -q < "$f"
done

pnpm typecheck && pnpm lint && pnpm test      # ۹۸۵ تست
```

**تضمین‌های پول** (هر وقت شک کردی، روی هر دیتابیسی امن است — همه‌چیز rollback می‌شود):

```bash
docker exec -i shikoo-sim-postgres-1 psql -U shikoo -d shikoo \
  -v ON_ERROR_STOP=1 -q < migrations/verify_invariants.sql     # باید ۱۹ تا PASS بدهد
```

**مهاجرت دیتای واقعی:**

```bash
pnpm --filter @shikoo/migrate preflight   # فقط می‌خواند — هیچ‌چیز نمی‌نویسد
pnpm --filter @shikoo/migrate migrate     # preflight → مهاجرت → تایید پولی
pnpm --filter @shikoo/migrate verify      # دوباره دو طرف را مقایسه می‌کند
```

**اجرای سرویس‌ها:**

```bash
DATABASE_URL=postgres://shikoo:shikoo_local@127.0.0.1:5433/shikoo \
  pnpm --filter @shikoo/ingest start       # پورت 8787

DATABASE_URL=... TEST_ACCESS_USER=you@example.com \
  pnpm --filter @shikoo/dashboard start    # پورت 8788

# ربات — بدون پورت، long polling. هرگز با توکن ربات واقعی.
# توکن را در sim/.env.local بنویس (git-ignored) و این را بزن؛ توکن به هیچ
# خط فرمانی و هیچ history شلی نمی‌رسد. فقط یک پروسه هم‌زمان می‌تواند poll کند.
pnpm --filter @shikoo/bot start:local
```

> `pnpm` روی ویندوز معمولاً روی PATH نیست. یا `corepack pnpm ...` بزن، یا یک شیم بساز:
> `%TEMP%\pnpmshim\pnpm.cmd` با محتوای `corepack pnpm %*` و آن پوشه را به PATH اضافه کن.
> اسکریپت `test` ریشه داخل خودش `pnpm` صدا می‌زند، پس بدون شیم کار نمی‌کند.

| `expected 53 tables, found 0`                           | اسکیما اعمال نشده                                                                                        | حلقهٔ `migrations/000*.sql` بالا را اجرا کن                                                                                                                       |

### آداپتور Postgres (`packages/db`)

| علامت                                              | علت                                                  | درمان                                                                                                        |
| -------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `could not determine data type of parameter $2`    | کوئری از قطعات اختیاری ساخته شده و `$2` استفاده نشده | خودکار حل می‌شود (`compactParameters`). اگر باز دیدی، خطا **خودِ دستور را چاپ می‌کند** — از همان‌جا شروع کن. |

| مقایسهٔ زمان یا مبلغ همیشه false                   | ستون `bigint` رشته برگشته                            | آداپتور `int8` را عدد می‌کند. بیرون از آداپتور کوئری نزن.                                                    |

| `INSERT OR IGNORE ... ON CONFLICT is ambiguous`    | هر دو با هم آمده‌اند                                 | یکی را بردار.                                                                                                |

## تله‌هایی که یک بار گازمان گرفتند

**۱. `Move-Item` روی پوشهٔ بزرگ نیمه‌کاره تمام می‌شود و خطا هم می‌دهد.** یک بار `.git` کامل این‌طور
رفت و بعد با `Remove-Item -Recurse` پاک شد. از `robocopy <src> <dst> /E` استفاده کن، قبل از حذف
مقصد را بشمار، و cwd هیچ شلی داخل پوشهٔ در حال جابه‌جایی نباشد.

**۲. `GROUP BY` در MySQL به بزرگی حروف حساس نیست.** بررسی اول من مقدار `active` (کوچک) را ندید
چون با `Active` یکی شمرده شده بود. هر بررسی مقدارِ یکتا روی MySQL باید `COLLATE utf8mb4_bin` داشته
باشد — **چک باید دست‌کم به سخت‌گیریِ کدی باشد که چک می‌کند.**

**۳. تستی که فقط با خودش سازگار است هیچ چیز را ثابت نمی‌کند.** باگ ۷ ساعتهٔ «امروز به وقت تهران»
سال‌ها زنده ماند چون تست‌ها فقط بررسی می‌کردند تابع با خودش می‌خواند. حالا با `Asia/Tehran` واقعی
سنجیده می‌شود.

**۴. جداسازی تست‌ها که از پلتفرم می‌آمد، با انتقال ناپدید می‌شود.** Workers به هر فایل تست یک
دیتابیس تازه می‌داد. با یک Postgres مشترک، چهار باگ فیکسچر بیرون زد که سال‌ها پنهان بودند.

**۵. دیتای seed از قبل تضمین پول را نقض می‌کرد** — و کسی نفهمید چون تست‌های seed مهاجرت `0011`
(همان که ایندکس‌های partial unique را می‌سازد) را اعمال نمی‌کردند.

## تصمیم‌هایی که نباید بی‌دلیل عوض شوند

- **تضمین پول در ایندکس است، نه در کد.** `idx_match_one_auto_per_tx` و
  `idx_match_one_auto_per_claim`. یک تراکنش بانکی حداکثر یک claim را تسویه می‌کند. **دلیل اصلی
  انتخاب Postgres همین است** — MySQL ایندکس شرطی ندارد.
- **پول همه‌جا `bigint` ریال.** تومان فقط در لبهٔ ربات وجود دارد.
- **کیف پول دفتر کل است.** هیچ کدی `wallets.balance_irr` را نمی‌نویسد؛ ردیف در `wallet_entries`
  درج می‌شود و تریگر مانده را جابه‌جا می‌کند.
- **`0004_payment_hub.sql` یک پورت مکانیکی است، نه بازطراحی.** اپاک میلی‌ثانیه `bigint` ماند و
  پرچم‌های ۰/۱ `smallint` — چون ۸۰۰ تست و کل `packages/domain` این ستون‌ها را می‌خوانند.
- **مهاجرت هیچ‌وقت پول را دست‌کاری نمی‌کند.** مانده منفی `-5,940,000` تومان عیناً منتقل می‌شود.
  تصحیح‌های آگاهانه فقط در `corrections.ts` با شواهدشان.
- **`legacy/` فقط مرجع است.** کد زنده نیست. در فاز ۵ حذف می‌شود.
- **آپدیت تلگرام در همان تراکنشی claim می‌شود که اثرش را می‌نویسد.** `handleUpdate` همه‌چیز را داخل
  یک `withSession` می‌گذارد و اولین کارش درج در `telegram_updates` است. اگر بعدش چیزی بترکد، claim
  هم rollback می‌شود و تحویل بعدی تلگرام یک تلاش واقعی است. جدا کردن این دو یعنی یا کیف پول دوبار
  شارژ می‌شود یا آپدیت بی‌صدا گم می‌شود.
- **پاسخ‌ها بعد از commit فرستاده می‌شوند، نه داخل تراکنش.** پیامی که رفته با ROLLBACK برنمی‌گردد.
  هزینه‌اش این است که یک پاسخ ممکن است گم شود؛ در ازایش دیتابیس هیچ‌وقت غلط نمی‌شود.
- **آفست long polling ذخیره نمی‌شود.** تضمین یکتایی فقط `telegram_updates` است — دو سازوکار که
  بتوانند با هم اختلاف پیدا کنند بدتر از یکی است.
- **`callback_data` ورودی کاربر است، نه توکنی که ما داده‌ایم.** تلگرام امضایش نمی‌کند و یادش نیست
  چه دکمه‌ای به چه کسی نشان داده؛ هر کسی با یک فراخوان ساده هر رشته‌ای می‌فرستد. پس شناسه‌ای که از
  آن می‌آید **هرگز به‌تنهایی ردیف انتخاب نمی‌کند**. هر خواندنِ ردیفِ متعلق به مشتری از `owned.ts` رد
  می‌شود که همهٔ کوئری‌هایش `AND user_id = $caller` دارند و تماس‌گیرنده آرگومان اولشان است، نه یک
  گزینه. ربات PHP همین را دستی در هر هندلر می‌گذاشت و در `subscriptionurl_` جا انداخت — مورد ۸
  `BUGS-FOR-ADMIN.md`. تستی هست که همان حمله را انجام می‌دهد.
- **آفستی که `pollOnce` برمی‌گرداند «رسید» است، نه بیشترین شماره.** تلگرام با گرفتن آن، هر آپدیت
  پایین‌ترش را **پاک می‌کند**. پس آفست فقط تا درست قبل از اولین آپدیتی که هندلرش ترکید جلو می‌رود.
  اگر از رویش رد شویم، rollbackِ claim هیچ چیزی نخریده — تلگرام دیگر آن را نمی‌فرستد. و وقتی
  دیتابیس خواب است این یعنی از دست رفتن **کل بسته**، نه یک پیام. آپدیت‌های بعد از خطا همچنان
  پردازش می‌شوند تا صف نخوابد؛ دور بعد دوباره می‌آیند و claim آن‌ها را `duplicate` می‌کند.
- **بسته‌ای که هیچ پیشرفتی نداشت، قبل از تلاش بعدی مکث می‌کند.** وقتی آپدیت در صف باشد
  `getUpdates` بلافاصله برمی‌گردد و long-poll نمی‌کند؛ اگر هندلرها هم بترکند هیچ چیز حلقه را کند
  نمی‌کند. اندازه‌گیری واقعی روی قطعیِ ۵ دقیقه‌ای Postgres: **۳۵۰ تلاش و ۶٬۳۶۳ خط لاگ**. با مکث،
  همان سناریو به ~۰.۱ چرخه در ثانیه رسید. بدون این، روی سرور واقعی از تلگرام `429` می‌گیریم و
  دیتابیسی را که دارد بلند می‌شود می‌کوبیم.
- **نشان‌داده‌شدن دکمه هیچ چیزی را اثبات نمی‌کند.** شرط دیده‌شدن یک محصول فقط یک بار نوشته شده
  (`PURCHASABLE` در `catalog.ts`) و مسیر ثبت سفارش **همان** را دوباره اجرا می‌کند. لیست با یک
  قاعده و فروش با قاعده‌ای دیگر، دقیقاً همان‌طور از هم فاصله می‌گیرند که در ربات PHP `config_`
  چک دارد و `subscriptionurl_` ندارد.
- **قیمت داخل همان تراکنشی از دیتابیس خوانده می‌شود که سفارش را می‌نویسد.** مشتری انتخاب می‌کند
  _کدام_ پلن؛ _چند_ دست او نیست. و تخفیف ایستادهٔ مشتری (`users.discount_percent`) واقعاً اعمال
  می‌شود — هشت مشتری پروداکشن ۱۰ تا ۱۰۰ درصد دارند و نادیده‌گرفتنش یعنی اضافه‌گرفتن از همه‌شان.
  قیمت فهرست روی ردیف سفارش می‌ماند تا فروش تخفیف‌خورده قابل حسابرسی بماند.
- **`answerCallbackQuery` بیرون از `handleUpdate` است.** آپدیت تکراری اصلاً به هندلر نمی‌رسد،
  ولی اسپینر دکمه‌اش باید بایستد؛ در قطعی دیتابیس هم باید بایستد، وگرنه ربات «هنگ‌کرده» دیده
  می‌شود.

### فاز ۴ — ربات جدید

جایگزینی **۴۰٬۳۶۷ خط PHP در ۸۸ فایل** (بدون `vendor/`، `lang/` و `vpnbot/`؛ با آن‌ها ۶۴٬۷۹۳ در ۱۰۴).
حجیم‌ترین بخش کل پروژه. سنگین‌ترها: `admin.php` ۱۰٬۸۸۸ · `index.php` ۶٬۸۲۶ با **۷۱۹ شاخهٔ dispatch**
در یک فایل · `panels.php` ۲٬۳۵۲. نُه آداپتور پنل هرکدام فایل جدا و ۹۱ تا ۴۸۱ خط‌اند، که یک‌به‌یک با
`provisioning_providers.kind` جور درمی‌آیند — یعنی پورت‌شدنی، یکی در یک زمان.

**ساخته شد (۲۰۲۶-۰۸-۱۲):**

- `migrations/0006_bot.sql` — `telegram_updates`. تضمین «دقیقاً یک بار» **در دیتابیس**، نه در کد.
- `apps/bot` — کلاینت تلگرام با اعتبارسنجی zod، حلقهٔ long polling، `/start`.
- `callback.ts` + `owned.ts` — دادهٔ دکمه ورودی بی‌اعتماد است و هر ردیف متعلق‌به‌مشتری فقط از
  یک جا خوانده می‌شود. علتش مورد ۸ در `BUGS-FOR-ADMIN.md` است.
- `menu.ts` / `catalog.ts` / `order.ts` / `money.ts` — منوی اصلی، مسیر خرید **پنل → محصول**،
  و ثبت سفارش در وضعیت `AWAITING_PAYMENT`.
- `seedCatalog()` در `packages/seed` — ۵ پنل، ۱۰ محصول، ۱۰ پلن، **بدون دسته**. idempotent، و
  ردیف‌های fixture قدیمی را که دیگر مالکشان نیست پاک می‌کند.

**هنوز نه:** پرداخت، کیف پول، کد تخفیف، تمدید، سرویس‌های من، تیکت، آداپتور provisioning،
پنل ادمین، کران‌جاب. بقیهٔ دکمه‌های منو به «به‌زودی» می‌خورند.

**شکل واقعی خرید — از روی دامپ ۲۰۲۶-۰۸-۱۱ تایید شد، نه از روی حدس:**

| شواهد                                | نتیجه                                                 |
| ------------------------------------ | ----------------------------------------------------- |
| `setting.statuscategory=offcategory` | مرحلهٔ دسته‌بندی خاموش است                            |
| جدول `category` صفر ردیف             | چیزی هم برای نشان‌دادن ندارد                          |
| `index.php:1507` bind می‌کند         | `product.Location` **نام پنل** است، نه یک دستهٔ مستقل |
| `setting.keyboardmain`               | چیدمان منوی اصلی، عیناً                               |
| `statusshowprice=offshowprice`       | قیمت در خودِ نام محصول تایپ شده                       |

پس مسیر خرید **پنل → محصول** است و بس؛ برداشت قبلی («دسته‌بندی بر اساس نوع سرویس») غلط بود.
سه انحراف عمدی از لگسی، با تایید Sam: پنل بی‌محصول نمایش داده نمی‌شود · نماینده همهٔ کاتالوگ را
می‌بیند (در لگسی `agent='n'` یعنی فروشگاه خالی) · دکمهٔ خرید تکراری سفارش باز را دوباره
برمی‌گرداند به‌جای ساختن فاکتور نو.

**تایید روی تلگرام واقعی، ۲۰۲۶-۰۸-۱۲، روی ربات تست:** سه `/start` → سه ردیف
`telegram_updates`، **یک** ردیف `users` با `registered_at` دست‌نخورده و `last_seen_at` تازه.
یعنی upsert واقعاً update کرد، و claim یکتا کار کرد — نه فقط در تست واحد، روی سیم.

بار دوم کل مسیر خرید با Playwright روی تلگرام وب رانده شد (`/start` → لوکیشن → محصول → مشخصات →
ثبت سفارش → ثبت سفارش دوباره). سفارش `8894451b49` با ۱٬۹۵۰٬۰۰۰ ریال ثبت شد و تکرار دکمه ردیف نو
نساخت. **سه چیز پیدا شد که از خواندن کد درنمی‌آمد:**

| چه دیده شد                                     | علت                                                               | درمان                                                      |
| ---------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------- |
| لاگ پر از stack trace موقع زدن دوبارهٔ یک دکمه | تلگرام به «پیام را با خودش عوض کن» جواب ۴۰۰ می‌دهد                | `editMessageText` فقط همین یک حالت را قورت می‌دهد          |
| دکمه قیمت را دو بار می‌گفت                     | نام هر محصول مهاجرت‌شده خودش قیمت را در خود دارد (`...-195.000ت`) | `nameMentionsPrice()` — اگر نام قیمت را گفت، اضافه نمی‌شود |
| ترتیب پنل‌ها با ربات زنده فرق داشت             | همهٔ پنل‌های مهاجرت‌شده `sort_order = 0` دارند و tiebreak نام بود | `ORDER BY sort_order, id`                                  |

**قیمت‌ها با حقیقت بیرونی سنجیده شدند:** هر هفت محصول پنل «مولتی لوکیشن» عددی که ربات ما نشان
می‌دهد دقیقاً همان عددی است که در نام محصول لگسی تایپ شده — ۱۰۰٬۰۰۰ تا ۵۵۰٬۰۰۰ تومان.

**از ربات زنده برداشته شد (فقط خواندن، هیچ دکمهٔ سازنده‌ای زده نشد):** منوی اصلی مو به مو با مال
ما یکی است · منوی خرید سه پنل دارد به ترتیب `marzban_panel.id` · «سرویس های من» صفحه‌بندی شده
(`بعدی`) و دکمهٔ «جستجو سریع» دارد · «کیف پول» صفحهٔ حساب کاربری است با تاریخ جلالی، موجودی،
تعداد سرویس، تعداد فاکتور، تعداد زیرمجموعه و گروه کاربری، و دکمه‌های «کد هدیه» و «افزایش موجودی» ·
پیام تایید پرداخت ادمین شامل نام کاربری سرویس، محصول، حجم، زمان، شناسهٔ مشتری، موجودی، کد پیگیری
۱۰رقمی هگز، مبلغ و کارت مقصد است، با چهار دکمهٔ تایید/رد/بلاک/شارژ دستی.
